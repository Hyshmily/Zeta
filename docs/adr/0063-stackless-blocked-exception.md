# Stackless `ZetaBlockedException` (Per-Read Control-Flow Exception)

Blocked keys are typically the highest-QPS keys in the system, and the block contract rethrows `ZetaBlockedException` on every read (`preGuard`/`afterGuard`), so the exception is a per-operation control-flow signal, not a fault record. Measured at a 64-frame call depth (JDK 26, dev machine, 5×300k rounds), construction cost is ~1.9 µs — ~1.7 µs of it `fillInStackTrace()`, ~0.1–0.2 µs the eager timestamp format + concat. `ZetaBlockedException` now constructs through a protected `ZetaContextException` channel with `enableSuppression=false, writableStackTrace=false` (~70 ns measured), and the base class formats `logMessage` lazily on first `getLogMessage()`/`getMessage()` access. The throw sites are fixed guards inside `HotKeyCache`, and `getSourceClass()`/`getCacheKey()`/`getTimestamp()` already carry the full diagnostics, so the stack trace's marginal diagnostic value is low; `getStackTrace()` returns an empty array by design.

**Consequences:** `ZetaBlockedException.getStackTrace()` is always empty — user code stringifying it loses the read-path call frames (the catching site knows its own context); `addSuppressed()` is a silent no-op (relevant only in the rare try-with-resources case whose primary exception is a blocked one). `ZetaModeException` keeps stack traces — mode violations are one-shot programming errors where the call site matters. The lazy `logMessage` is a volatile benign race: every input is final, so a concurrent first access formats twice and one identical write wins.

**Considered options:** keeping stack traces (forfeits ~90% of the win; the frames below the fixed guard are only mildly informative), an opt-in flag on the constructor (no caller wants the slow path), overriding `fillInStackTrace()` to return `this` (same effect, less conventional than the JDK 9+ constructor flag).

Companion cleanup in the same pass: `ZetaExceptionHandler.handleException(context, t, fallbackToWarn)` resolves the handler exactly once; `HotKeyCache.executeCore` uses it with `fallbackToWarn=false` instead of the probe-then-act `getExceptionHandler() != null` pre-check, removing the double resolution (and the duplicate-log race) on the read-error path. The two-argument `handleException` delegates with `fallbackToWarn=true` — behaviour unchanged for executors.

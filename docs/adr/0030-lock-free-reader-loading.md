# Lock-Free Reader Loading: No User I/O Under the Caffeine Bin Lock

`computeIfAbsent` / `computeIfAbsentWithSoftExpire` — the single read entry for `@Cacheable` (ADR-0023) — previously ran the user reader, potentially network I/O, inside Caffeine's `asMap().compute()` callback. A slow reader held the hash-bin lock for its full duration, stalling every other key in the same bin (concurrent reads, `putThrough` writes, promotions, and Worker decisions all contend on the same bins), and the reader had no timeout and no circuit-breaker participation. We decided the compute callback must be a fast, I/O-free critical section: state checks and pure TTL re-computation only. On a miss or a REVALIDATE soft-expiry the callback returns `null` (or keeps the stale entry), and the reader runs *outside* the lock via `SingleFlight.load` — inheriting dedup, timeout, and circuit-breaker protection; the loaded value is then written by a short second compute through the same `processLoaded`/`loadCacheEntry` machinery as the `get` read path, unifying the two read paths. The same rule was applied to `DefaultWorkerDecisionHandler.handleHot`, whose entry-absent branch read the Redis dataVersion inside the compute; the version is now pre-read before the lock, gated by a DCL pre-check so the common existing-entry path pays nothing.

**Consequences (each behavioral change aligns `computeIfAbsent` with the `get`/`getWithSoftExpire` path):**

- **Loader thread affinity.** The reader executes on the SingleFlight executor thread (`hotKeyExecutor`), not the caller thread. ThreadLocal state prepared by the caller (request context, transaction, security context) is not visible inside the loader on a miss. This was already true for `get`/`getWithSoftExpire`; it now also applies to `@Cacheable` method bodies and direct `computeIfAbsent` callers.
- **Timeout and circuit breaker.** The reader is now bounded by `zeta.local.inflight-timeout-seconds` and records failures into the circuit breaker; the pre-refactor `computeIfAbsent` path had neither.
- **Hard-expired entries are never served as stale.** On load failure a hard-expired entry is removed (it was already removed by the miss path), matching `get` — previously the in-lock CB fallback could return a hard-expired value.
- **REVALIDATE keeps the soft-expired entry.** A failed REVALIDATE reload leaves the stale entry in L1: the circuit-breaker fallback can still serve it (graceful degradation, ADR-0021) and the next call retries. Deliberate divergence from `getWithSoftExpire`, which invalidates first; bounded by the hard TTL.
- **Lazy TTL actually enforced.** ADR-0023's lazy-TTL contract was violated by eager `getAsLong()` calls before the compute; TTL suppliers (SpEL) are now evaluated only when an entry is created, promoted, renewed, or a refresh is scheduled — a plain NORMAL hit never resolves them.
- **SOFT_REFRESH triggered outside the lock.** The background-refresh trigger moved out of the compute callback, removing a nested `pendingRefreshes` lock acquisition. The remaining divergence is NORMAL entries, which `computeIfAbsent` refreshes (the `@Cacheable` path, where the default SOFT_REFRESH policy depends on it) while `getWithSoftExpire` does not (it uses short TTLs instead); see below for the COOL-specific handling.
- **COOL entries refresh on soft expiry, and a successful refresh downgrades them to NORMAL.** Both read paths trigger the SOFT_REFRESH background refresh for COOL entries when a reader is present (`refreshSoftExpire` gates on Worker-managed HOT/COOL, `computeInLock` checks `reader != null`); a null reader (convenience policies) skips the refresh — an explicit gate, **not** `softTtlMs = 0`, because `isSoftExpired(0)` is deliberately true and would otherwise trigger a refresh on every hit. A successful COOL refresh downgrades the entry to `KeyState.NORMAL` (`applyRefreshTask`, both the existing-entry and the rebuild branch): the local read that caused the refresh shows the key is still active locally, so it returns to the ordinary local lifecycle — promotion-eligible, and on the `getWithSoftExpire` path no longer proactively refreshed (NORMAL uses its short TTLs and a hard-TTL reload; the asymmetry is deliberate — the TTL exists to force a reload, not to be defeated by endless background refreshes). Decision metadata is preserved, so a later Worker broadcast still overrides via `decisionVersion`. NORMAL/HOT refreshes keep their state.
- **COOL fallback TTL unit fix.** `COOL_DEFAULT_PROTECTION_HARDTTL_TIME`/`SOFTTTL_TIME` (120/60) were declared in seconds but passed to millisecond APIs; when an entry had no normal TTL configured, a COOL entry lived for 120ms instead of 120s. The constants now carry millisecond values (120000/60000).

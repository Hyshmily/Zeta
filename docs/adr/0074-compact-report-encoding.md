# Compact Binary Encoding for App→Worker Report Messages

`ReportMessage` batches traveled as Jackson JSON bodies on both the App-side `zetaReportRabbitTemplate` and the Worker-side `reportListenerContainerFactory`. For a typical key-count batch (counts are 1-2 digit integers) JSON pays a per-entry `"key":N,` framing overhead of 4-5 bytes plus structural fields, inflating AMQP frame count and Worker-side parse cost. We add an opt-in compact binary encoding for the report wire format — varint continuation encoding with length-prefix framing, adapted from RocksDB `util/coding.h` — selected by configuration on the send side and auto-detected on the receive side.

## Status

accepted

## Context

1. **The wire format is ADR-0067 territory.** The sync plane's rolling-upgrade rule ("wire-compatible in both directions") was written for `SyncMessage`; the report plane had no such constraint on record, and ADR-0071 documents that an unknown wire format in a mixed cluster *drops* messages (the Worker's poison-message path logs and discards without requeue). Any format change therefore needs an explicit compatibility story, not just a codec.
2. **The two planes differ structurally.** `CacheSyncPublisher` already hand-frames bodies (raw UTF-8 key + AMQP headers for single-key messages) — there is nothing for a codec to win there. `ReportMessage` is the one JSON-serialized payload with high fan-out (every flush cycle, every App instance), which makes it the only worthwhile target.
3. **Jackson defaults on both sides.** Common's `zetaReportMessageConverter` and Worker's fallback `reportMessageConverter` are both `Jackson2JsonMessageConverter` beans, so a binary body must be introduced as a converter concern, not a record change — the record stays the in-memory model.

## Decision

- New `reporting/ReportMessageCodec`: static `encode`/`decode`/`isCompact`. Wire layout: `[0]` magic `0x5A` ('Z'), `[1]` version `0x01`, then varint64 id, varint64 timestamp, varint32-framed UTF-8 appName, varint32 entry count, and per entry a varint32-framed UTF-8 key plus varint64 count. Every read is bounds-checked — truncated bodies and absurd length fields throw `IllegalArgumentException` instead of allocating (deserialization-DoS guard); the entry count is additionally rejected once it exceeds what the remaining body could hold. Null `appName`/`counts` are rejected at encode (JSON can express null; the compact format cannot, and the production path never produces them).
- New `reporting/CompactAwareReportMessageConverter` wrapping the Jackson delegate. **Encode** follows configuration; **decode is always dual-format** by first-byte sniffing (`0x5A` → codec, anything else → Jackson). This is the compatibility contract: upgrade Workers first (they decode both), then flip Apps to compact — a mixed cluster loses no reports, and old Apps never see a compact body.
- Configuration: `zeta.local.report-encoding` (`ZetaProperties.ReportEncoding`, enum `JSON`/`COMPACT`, default `JSON`). Worker-side decode needs no setting because sniffing subsumes it; the Worker fallback converter is wrapped with encode=disabled (Workers do not emit reports).
- Content type of a compact body is `application/octet-stream`; the `__TypeId__` header is left as Jackson writes it on the JSON path.

## Considered Options

- **Compact-encode `SyncMessage` too:** single-key sync messages are already header-framed raw bytes (win <10%); `INVALIDATE_ALL`/`RULES_SYNC` bodies are low-cadence. Rejected — complexity without measurable benefit.
- **Version negotiation via headers instead of body sniffing:** headers can be stripped or missed by intermediary tooling; the magic byte lives in the body itself and costs nothing to check. Rejected in favor of sniffing.
- **Always-on compact (no config):** forces the flip in the same release as the Worker upgrade window, removing the operator's control over mixed-cluster timing. Rejected — the flag defaults to `json` so adoption is a deliberate second step.
- **ByteBuffer-based codec:** one more abstraction over a body we fully frame ourselves; the hand-rolled `byte[]` + cursor keeps the decode allocation-free except for the key strings. Rejected.

## Consequences

1. Typical batches shrink materially (the structural per-entry overhead drops from ~10-14 bytes to ~2-3 bytes plus the varint count); actual savings depend on average key length and are asserted directionally in `ReportMessageCodecTest` rather than promised numerically.
2. `zeta.local.report-encoding=compact` before all Workers are upgraded is the only foot-gun, and it is safe on the *decode* side by construction — the flag only controls encoding. Rolling-upgrade guidance: Workers first, then Apps.
3. `ReportMessageCodecTest` (round-trips across ASCII/Unicode/long keys/boundary varints, size comparison against an equivalent JSON rendering, truncation sweep, malformed length fields) and `CompactAwareReportMessageConverterTest` (encode flag, sniffing, poison-message exception mapping) pin the contract; `ZetaAmqpAutoConfigurationTest` and `ZetaMicrometerAutoConfigurationTest` were adapted to the new bean signatures.

## Follow-up: decode hardening, and the measured baseline for the rejected ideas

A review of `ReportMessageCodec` proposed nine changes: a `ByteBuffer` encode, a dedicated 32-bit varint reader, integer capacity math, scratch reuse, an absolute entry-count cap, non-null key checks, non-negative `id`/`timestamp` assertions, a unified `ByteBuffer` codec, and a shared varint utility. They were measured before any of them was implemented, on **Intel Core Ultra 9 285H / OpenJDK 64-Bit Server VM 26 / Windows 10.0.29667**, using `ThreadMXBean.getThreadAllocatedBytes` over a 2,000-entry batch of 40-byte keys (85,007-byte body); the JUnit runs below used **JDK 21 / Maven 3.9.14**. The harness lives in `sandbox/codec-probe/`: `Probe.java` plus `snapshot_baseline.py`, which freezes the pre-change class so old and new are measured inside one JVM.

### Landed

1. **Guards no longer build their message eagerly.** `Assert.isTrue(cond, msg)` evaluates `msg` before the call, so the two dynamic guards that run **per entry** (`requireRemaining` for the key length, `readVarint32`'s range check) fabricated a ~64-character string for every key of every *successful* decode. They are now `if (!ok) throw new IllegalArgumentException(...)`. Measured on the batch above: decode allocation **584,376 → 263,968 bytes (-54.8%)**; every-call fixed cost **674 → 136 bytes**; decode CPU (interleaved, minimum of 25 rounds, three runs) **≈124-132 µs → ≈76-77 µs per batch (-38%)**. This one change outweighs the entire fixed cost that the rejected fixed-cost items would have touched.
2. **A varint whose tenth byte overflows the accumulator is rejected.** Nine continuation bytes put the final byte at shift 63, where Java's modulo-64 shift discards all but the lowest bit: the body `80 ×9, 7F` decoded to `Long.MIN_VALUE` — byte-for-byte different from, but semantically identical to, the canonical encoding of `Long.MIN_VALUE` — with no error raised. Only `0x00`/`0x01` are accepted in that position now.
3. **Malformed UTF-8 is rejected instead of substituted.** `new String(bytes, UTF_8)` maps ill-formed input to U+FFFD, so a forged body could decode into a key that was never sent and propagate it into the Worker's TopK state. `isWellFormedUtf8` now validates first (RFC 3629: overlong forms, surrogates, above U+10FFFF, stray continuation bytes, truncation). It allocates nothing, and an ASCII fast path (one 64-bit load per eight bytes, masked for high bits) keeps it off the hot path: a byte-at-a-time version cost **+24.5% decode CPU** against the baseline, while the fast-path version is a net **-38%** together with item 1. It is differential-tested against the JDK decoder in `REPORT` mode over every one- and two-byte input, the three- and four-byte boundary grid, and 70,000 seeded random inputs.
4. **Trailing bytes are rejected.** Decode ignored anything after the last entry; a magic-sniffing receiver otherwise has no way to notice that sender and receiver disagree about the layout.
5. **The result map is pre-sized with a capped hint** (`Math.min(entryCount, 4096)`) instead of `entryCount`. The count is attacker-controlled and bounded only by the body length, so it could drive a large up-front table allocation; `HashMap` grows on demand, so the cap costs nothing. Measured on bodies made of 2-byte entries: allocation per decode **38.9 MB → 4.8 MB**, input-to-allocation amplification **97× → 12×** (a realistic 40-byte-key batch sits at **6.9×**).
6. **Encode sizes the body exactly instead of guessing a capacity.** The old path wrote into `new ByteArrayOutputStream(64 + counts.size() * 16)`; that hint assumes ~14-byte keys, so the 40-byte-key batch overshot it 2.7×, the stream doubled its buffer twice (32,064 → 64,128 → 128,256) and `toByteArray()` copied the finished body once more. A first pass now computes the exact length — `varlongLength` plus `utf8Length`, the latter exact for every `char` including the single-byte `'?'` the JDK encoder substitutes for an unpaired surrogate — and the write goes into that one array, whose final cursor is checked against the computed size. Measured: encode allocation **421,608 → 197,056 bytes (−53.3%)**, and what remains decomposes completely — result array 85,024 + one `byte[]` per key 112,000 + 32 bytes unaccounted. No buffer, no growth, no copy. A plain-JDK reconstruction of the old path (same call shape, same hint, `getBytes` included) allocates 420,544 bytes against the measured 421,608, which is what lets the 139,472-byte growth term (33.1% of the old total) and the ~84,000-byte final copy (20.0%) be attributed. The `getBytes` temporaries that remain are 57% of what is left, and are the next thing worth removing.

### Rejected, with the measurement that settled it

- **`ByteBuffer`-based encode/decode (and the unified codec):** the proposed estimator `20 + appName.length() + entryCount * 24` overflows on ordinary data — it threw `BufferOverflowException` on the existing `roundTrip_longKeys` fixture (a single 10,000-byte key) and on 200 keys of 29-31 bytes. `String.length()` is a char count rather than a UTF-8 byte count, so a Chinese app name is under-counted threefold, and `entryCount * 24` silently assumes keys ≤ 22 bytes. And the fixed cost it would have attacked is negligible: **232 bytes per encode** and **679 bytes per decode**, against totals of **421,608** and **584,376** bytes for this batch — 0.06% and 0.12%. Two corrections to that reasoning, both from later measurement: those totals bound only the *fixed* cost, and encode's buffer growth and final copy were separate size-proportional terms the 0-entry probe could not see (together 53% of encode — item 6 above); and the snippet's estimate-then-copy shape would have added a second full copy where `toByteArray()` already costs one, whereas the landed two-pass exact size removes the copy rather than doubling it.
- **A dedicated 32-bit varint reader:** `readVarlong` returns at the first byte without a continuation bit, so it iterates once per encoded byte — measured 1 iteration for `1` and `127`, 2 for `128` and `1_000`, 5 for `Integer.MAX_VALUE`. The claimed "five wasted iterations per call" does not exist.
- **An absolute `MAX_ENTRIES` cap:** the existing `entryCount <= (end - pos) / 2` guard already bounds the pre-size hint by the body length (a table of at most ~5.3 bytes per input byte), and the amplification is dominated by per-entry work, which a count cap does not change. A decode-side count limit is also a wire-compatibility change — a sender above the limit would be classified malformed and its reports dropped, the exact mixed-cluster failure this ADR exists to prevent. Capping the *hint* gives the same protection with no format impact.
- **Non-negative `id`/`timestamp` assertions on encode:** `ReportMessageCodecTest.roundTrip_boundaryCounts` pins negative values as varint-safe, and that contract stands.

### Consequences of the follow-up

1. **The compact body is byte-identical for every input the encoder produces.** The decode-side changes reject only input the encoder never emits, and the encode rewrite is pinned by the golden-byte tests (they assert exact bytes and were not modified by it). Rolling-upgrade guidance is unchanged (Workers first, then Apps).
2. **A `VERSION` bump is an upgrade event.** A body carrying a newer version still matches the magic byte, so it fails as a malformed body rather than falling back to JSON. Bumping the version needs the same Workers-first sequence as the original flip, and is safe only once every receiver accepts both versions.
3. **The byte string is not canonical**, now stated in the class javadoc: `counts` is a `HashMap` (iteration order depends on insertion history and capacity) and decode accepts non-minimal varint encodings. Do not hash, dedupe or fingerprint bodies on their wire representation.
4. `ReportMessageCodec` no longer depends on `org.springframework.util.Assert` or on `java.io.ByteArrayOutputStream`: its guards are plain `if`/`throw` and its body is one exactly-sized array. That is what makes "nothing discarded is allocated on the success path" hold at every JIT tier rather than only once escape analysis kicks in.
5. New tests pin what the previous suite could not see: a literal 12-byte golden body and a field-by-field golden body for the `sample()` batch (`encode`∘`decode` round-trips are blind to a layout change that stays self-consistent, and the golden bodies are what confirm the rewrite produced identical bytes), exhaustive truncation, trailing bytes, the tenth-byte overflow, malformed UTF-8 in a key and in the app name, a batch of 5,000 entries against the capped pre-size hint, a 20,000-case random-mutation sweep (only `IllegalArgumentException` may escape), the UTF-8 validator's differential tests, and `utf8Length` differential-tested against the JDK encoder over every BMP `char`, surrogate pairings and 70,000 random strings — plus a lone-surrogate encode case, which fails loudly rather than silently if the two passes ever disagree.
6. **An unpaired surrogate in a key is replaced, not preserved.** `String.getBytes(UTF_8)` substitutes a single `'?'`, so a key containing one does not survive the round trip. This predates the follow-up, is now pinned by a test, and is the one input for which encode is not injective; cache keys in practice are well-formed, or come from byte-level sources that never entered a `String`.

## Follow-up: second review round — pre-size drift and two real decode gaps

A second review of `ReportMessageCodec` produced nine proposals. Five were real and are landed; the rest re-litigated decisions recorded above or misread the code (details under "Rejected again").

### Landed

1. **The pre-size hint is restored to the decision recorded in item 5: `Math.min(entryCount, MAX_PRESIZE)`.** The cap had landed with an extra shaping — `(Math.min(entryCount, 4096) >> 2) / 3 + 1` — an inverted load-factor adjustment (the standard ×4/3 became ÷12) that this ADR's own text never described. A 4,096-entry batch pre-sized at ~342 and grew the result table through four resizes. The hint is again the capped entry count: the up-front table is bounded at 4,096 slots (≈32 KB), still clamped by `entryCount ≤ (end − pos)/2`, and a 5,000-entry batch now grows the table exactly once.
2. **`readVarint32` rejects the negative-long window.** Values in [2^63, 2^64) leave `readVarlong` as negative longs, which the old `value > Integer.MAX_VALUE` check let through, truncating a forged length to its low 32 bits: the ten-byte varint for 2^63+5 decoded as length 5 — a wrong value accepted as success, against the reject-don't-repair doctrine. The check is now `value < 0 || value > Integer.MAX_VALUE`; the dedicated 32-bit reader stays rejected per the measurement above.
3. **`readUtf8` builds its error message on the throw path only.** Its `what` argument is a runtime value, so the guard-helper form concatenated `MALFORMED_MESSAGE + what + …` on every successful key decode — the exact eager-message cost item 1 removed elsewhere (readUtf8 postdates that fix and reintroduced the pattern). The constant-message guards need no change: `MALFORMED_MESSAGE + "…"` is a compile-time constant expression, folded by javac into one interned string.
4. **Encode rejects an overflowed size.** The sizing accumulator can wrap only for maps far beyond any real batch; a `size < 0` guard turns the resulting `NegativeArraySizeException` into a clear `IllegalArgumentException` before the allocation.
5. **Maintenance.** The guard class `UNSAFE` keeps its name but now carries javadoc stating it never touches `sun.misc.Unsafe` and recording the constant-message rule `check` relies on; per-entry null keys/values fail with named messages instead of bare NPEs; javadoc records that a duplicated key keeps the last occurrence and that `counts` must not be mutated while encode runs (the production path encodes a drained snapshot). New tests pin the 2^63+5 rejection and the last-wins behavior.

### Rejected again

- **Absolute body/entry/key caps:** decode is already O(body) bounded — `entryCount ≤ (end − pos)/2`, every length checked against the remaining bytes, and the body itself bounded by the broker's frame_max — so a codec-level cap adds no security while converting "operator raises frame_max" into silently dropped reports, the mixed-cluster failure this ADR exists to prevent.
- **Rejecting negative counts/timestamps:** `roundTrip_boundaryCounts` pins them as varint-safe; that contract stands.
- **Rejecting duplicate keys via `putIfAbsent`:** the encoder never emits duplicates and last-wins matches map semantics; the behavior is now documented rather than policed.
- **"Hot-path string concatenation" in the varint checks:** those message arguments are compile-time constants — no success-path allocation exists to remove.

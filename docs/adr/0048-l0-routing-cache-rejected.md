# ADR-0048: Per-Writer L0 Routing Cache — Rejected (Measured Net Loss on Real Hardware)

The three-tier routing proposal (极热 / 热 / 冷) added a per-writer multi-key fast-claim cache (L0) between the last-key cache and the routing beacon: the last-key cache covers ONE key, so a writer whose stream ALTERNATES among a small set of hot keys pays the beacon test and the local-map probe on every key switch; an L0 of the recently claimed slots was proposed to skip both. We validated the idea through the full pipeline — sandbox routing simulation, a Java prototype with exactness tests, and a real-hardware benchmark — and REJECTED it: the direct-mapped shape (dm256) measured a net LOSS in 4 of 5 workloads (−8.0% to −20.5%) and the original linear-scan sketch (scan32) lost everywhere (−8.5% to −48.0%); the sandbox's stylized cost model overestimated the hit savings because in the real counter the fixed `count()` context (~10ns: thread-local get, shutdown opaque read, batch-size check) dominates, making the dm hit path and the beacon+probe path nearly identical in cost. The prototype was reverted; the routing layer stays two-tier (last-key cache + beacon).

**The sandbox measurement (`l0_routing_sim.py`, 120-seed fuzz, paired per seed — routing hit rates + a stylized cost model).** The linear-scan candidate (the user's sketch: fixed 32-slot array, FIFO eviction, hits do not move) is a net loss on the median random workload (+9.25 ns/op, 17.5% win rate — the full-scan miss cost; the cost curve is U-shaped in k, optimum k≈4-8, and k=16+ loses in almost every model). The direct-mapped variant (dm256: one masked load + one pointer compare, fixed miss cost) wins in 100% of the random workloads (−2.4 ns/op median). Two structural findings stand regardless of the cost model: (1) scan-FIFO churns under intruders — other writers' hot keys entering via the global tail evict the writer's own keys (rr8: scan8 hit 50% vs dm64 83%); (2) long-key sensitivity (hot-path equals 20ns) rescues the scan only in strong-locality models, never in zero-locality ones.

**The Java prototype (`WaveCounter.java`, behind a package-private `L0Mode` knob, production default NONE).** Both candidates implemented inside `Ceils` with the existing exactness protocol: L0 entries are claim-recorded, stale entries (drained/re-claimed slots) are detected by a `keys[slot] == key` re-verification, racing drains are resolved by the 0-return recovery and steered by the drain stamp, and the pool reset wipes the arrays. Unit tests proved EXACTNESS — no loss, no double count, no mis-attribution — across claims, tide drains, 4-writer × 6-tide drain races and the pool reset, for both shapes; the NONE mode (the production default) was untouched (140/140 doublebuffer tests). The implementation also surfaced a JIT lesson: the first (monolithic, two-mode, loop-bearing) `tryL0Add` was NOT inlined into `count()` and measured ~3x the isolated-path cost (−24% in the alternating workload); splitting it into tiny per-mode methods restored the expected per-op cost.

**The real-hardware benchmark (16 threads, 5 interleaved 6s runs per workload, dedicated JVM, 8g heap — the interleaving and dedicated JVM are load-bearing; a naive ordered run swings ±15%).**

| Workload | L0 hit rate | dm256 | scan32 |
| --- | --- | --- | --- |
| alt2 (per-writer alternating pair) | 100% | **+2.7%** | −8.5% |
| zipf09 (global Zipf s=0.9, 10k keys) | ~72% | −8.0% | −34.6% |
| aff8 (90% per-writer 8-key set) | ~65% | −12.6% | −46.4% |
| rr8 (90% round-robin 8-key set) | — | −20.5% | −45.2% |
| aff8long (~60-char keys) | — | −19.8% | −48.0% |

**Root cause — why the sandbox was wrong.** The sandbox modeled only the routing steps (beacon ≈ 3ns, probe ≈ 3ns, dm probe ≈ 2.5ns). In the real counter every op first pays the fixed `count()` context (ThreadLocal get, shutdown opaque read, batch-size check ≈ 10ns), and the beacon+probe path is CHEAPER than modeled (the probe usually hits at rank 0-1, the equals is fast on short keys, and the JIT handles the beacon path well): the measured dm hit path (~17.9ns) and beacon+probe path (~18.3ns) are nearly identical, so the hit savings are ~0.4-2ns — not the modeled 3.5ns — while EVERY non-lastKey op (including every cold op) pays the dm probe's extra ~2-3ns. The net is negative unless the hit rate approaches 100% (only the pure-alternation workload got there). Long keys did NOT rescue it (aff8long −19.8%): the equals saving is real but the shared fixed overhead swamps it.

**Decision.** Reject the L0 (both shapes) for the default path; revert the prototype from `WaveCounter.java` and delete the prototype tests/benchmarks (the ADR-0038 validation-before-wiring precedent: the probe is deleted, the ADR is the record). The alternating-hot-keys pattern remains covered by the beacon path at its measured ~18ns/op, which the L0 could not measurably beat. The sandbox files (`l0_routing_sim.py`, the l0_* PNGs) are retained as the routing-layer measurement record.

**Considered options.** (1) **scan32** — rejected: full-scan miss cost + FIFO intruder churn, measured −8.5% to −48.0%. (2) **mtf variants (move-to-front)** — the swap cost (1ns/hit) erodes the scan's hit-rate advantage on short keys; same U-shaped structure; not implemented in Java after the scan shape's measured defeat. (3) **dm256 as an opt-in knob (keep the prototype)** — rejected: the measured loss in 4/5 workloads and the +3KB per-writer memory (256 × ref+slot) do not justify the code surface; resurrect from this ADR if a deployment shows per-writer alternation at ~100% locality AND long keys. (4) **A shared/global L0** — rejected by design: shared access on the super-hot keys is exactly the contention the hot path's per-writer maps avoid. (5) **Raising the beacon's k** — different problem (membership accuracy, not claim-speed).

**Consequences.** `WaveCounter.java` is back to the two-tier routing with zero extra per-writer memory; the exactness tests for the L0 shapes were removed with the prototype (the ADR is the record). The sandbox's ROUTING findings remain valid (hit-rate curves, the scan's U-shaped cost, the rr8 FIFO-churn discovery); its COST MODEL does not transfer to real hardware — the fixed `count()` context dominates, so routing-layer micro-optimizations of this scale cannot measurably move throughput. Future routing proposals should benchmark the full counter from the start instead of extrapolating stylized per-op costs.

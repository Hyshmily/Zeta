# Exception Escalation Policy: Swallow by Default, `failOnError` Escape Hatch

Read-path failures (loader exceptions) are swallowed into cache misses by default — a failing data source is indistinguishable from an absent key, and programming errors in the loader surface as "no data" instead of stack traces. We added an opt-in `failOnError` flag on `CachePolicy` (via `CachePolicy.of(reader).withFailOnError()`, or the `failOnError` parameter on the batch `get`/`getWithSoftExpire` overloads) that rethrows read-path `RuntimeException`s to the caller, so 500s stop masquerading as 404s.

The swallow-by-default contract is unchanged: `execute` still logs ERROR (and routes to the `ZetaExceptionHandler` chain when a handler is installed), returns `Optional.empty()`, and keeps the caller operational. `failOnError` deliberately covers the whole read path, not just the loader — internal side-effect failures (reporting, promotion) also propagate, because classifying exceptions by type (expected vs programming error) is a dangerous heuristic; the caller is the honest boundary for that decision. `null` loader results are untouched by the flag: they remain empty results cached as `NullValue` sentinels, so "no data" stays distinct from "data source failed" without extra signaling.

The batch path needed its own plumbing: `SingleFlight` gained a `default` three-argument batch `load(Iterable, Function, boolean)` where `failOnError = true` aborts the whole collection with the first failure cause (mirroring the single-key path's rethrow in `handleFailure`); the default implementation preserves the legacy swallow behavior. Timeouts and circuit-breaker interception resolve to empty results in both modes — they are transient degradation, not failures. In `computeInLock` (the `computeIfAbsent` path), a `failOnError` loader failure rethrows inside the Caffeine `compute` lambda, which aborts the mapping and leaves any pre-existing entry untouched rather than deleting it.

**Consequences:** the `CachePolicy` record gained a component (a source- and binary-breaking change for direct constructors; factory-based consumers are unaffected since factories default the flag to `false`). The `ZetaExceptionHandler` chain is now also invoked on the synchronous read path (previously executor-bound only), which is safe because the chain never throws. The state machine evaluation catch in `ZetaBayesianSM` was upgraded from DEBUG to WARN as part of the same observability pass — state-machine exceptions are genuine faults, not expected edge cases.

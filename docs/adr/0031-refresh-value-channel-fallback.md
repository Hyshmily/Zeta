# REFRESH Value-Channel Fallback: Invalidate When No Redis Value Exists

The cross-instance REFRESH broadcast (sent by `putThrough`, which is what `@CachePut` routes through) never carries the value — the receiver loads it from Redis via `RedisCacheLoader`. But nothing in Zeta ever writes the cache-key namespace in Redis (only rule and lock keys are written), so in the default wiring a REFRESH could never deliver its payload: the receiver logged a WARN and kept whatever was in L1, silently stale, while the `dataVersion` kept incrementing. We decided the REFRESH handler falls back to a **local invalidation** when the value cannot be loaded: the next read on that instance reloads through the type-safe application reader. This restores write consistency for `@CachePut` (a peer's copy is evicted and refetched) at the cost of losing the push-style freshness — acceptable, since the push channel was dead anyway. The fallback is local-only (no version record, no re-broadcast), so it cannot loop. If an integration does maintain Redis values itself, the push path still works and is preferred.

**Related correctness fixes recorded with this ADR:**

- **Worker decision identity on the HOT create path.** `handleHot` created entries for absent keys via a `createBuilder` overload that omitted `decisionNodeId`/`decisionEpoch` (defaults null/0). `VersionGuard.shouldSkipForWorker` treats epoch 0 as "always older" and null nodeId as "different node" — both accept unconditionally — so out-of-order replayed decisions could overwrite a freshly Worker-created entry. The create path now uses the overload that preserves the full decision identity.
- **Snowflake worker seed.** `resolveWorkerId` used the local IP's last octet, which collides for multiple instances on one host (containers). It now derives the 8-bit worker id from the JVM-unique node id XOR the process id, so degraded versions (`Long.MIN_VALUE | snowflakeId`) stay distinct across instances on the same host.

# ADR-0056: Logical hotLimit — Rejected (Sandbox No-Win Check)

The proposal to split `hotLimit` into a fixed PHYSICAL beacon capacity (e.g. 4096 rooms) plus a controller-driven LOGICAL hot-set size (range `[MIN, MAX]`, adapting to the business cycle) was evaluated in the zeta-tidal-sim sandbox with a paired 120-seed campaign against an ORACLE variant (perfect per-tide knowledge of the true hot-set size, zero lag, zero controller cost — an upper bound no real controller can beat) — and REJECTED: on business-cycle workloads whose true hot-set size sweeps across the shipped default (1024), the oracle is behaviorally IDENTICAL to a fixed `k = 1024` under the same physical shape on every governor axis (arms / excess / floor_max / harmful over-filter / flicker / admit latency, all exactly 0 for both), and its only gain — hot-path routing coverage (+0.227, 120/120 seeds, p < 0.0001) — is exactly the marginal-tail routing precision the Java bench already measured as throughput-free (the cold path carries un-promoted hot keys without measurable loss, `WaveCounter.java` DEFAULT_HOT_LIMIT doc). A real controller (signal lag, oscillation risk, two-dimensional governor coupling, P1/P2/confirm-admit adaptation) cannot beat an upper bound that gains nothing; the fixed 1024 stays.

**The sandbox check (`hotlimit_no_win.py`, 120 paired seeds, `hotlimit_no_win_120.log`).** Workloads: business-cycle tides (cycle / spike / drift / walk shapes, 48-96 tides) whose true hot-set size n(t) sweeps 50-3500 — deliberately straddling 1024 — with partial per-tide roster churn (0-50%); every roster key is counted at exactly 200/cycle, so the qualifying set at the histogram boundary IS the roster by construction and capacity is the only variable under test (the promotion floor stays inert: boundary 200 >> floor 10). Variants, all under the shipped governor + ADR-0054 exact selection:

**Finding 1 — adaptivity is worth nothing on the behavior axes.** `oracle` and `fix1024_prop` are byte-identical on every governor metric (both exactly 0 for arms/excess/floor_max/over-filter/flicker/admit latency; the paired deltas vs fix1024 are identical for the two variants). The oracle's only delta is coverage (+0.227 over the fixed-k shape, +0.289 over shipped 1024). Coverage is ROUTING precision of the marginal tail, not detection coverage: both consumers (`HotKeyDetector`, `KeyReporterImpl`) receive the full snapshot regardless of routing, and the Java bench's measured fact is that the cold path absorbs the overflow without throughput loss. Within the physical ceiling the oracle is also trivially equivalent to fixing `k = max` (oracle == fix4096 on all axes): the only regime where logical k < physical would ever differ is the one the proposal explicitly excludes (n(t) beyond the physical ceiling).

**Finding 2 — the proposal's own shape pays the measured per-op penalty permanently.** The physical-4096 shape reads a 64 KB beacon on every count — the exact configuration measured +16-36% SLOWER than 16 KB on the 16-thread sweep (`WaveCounter.java` DEFAULT_HOT_LIMIT doc). The logical limit cannot shrink the array's cache footprint; the only footprint-saving implementation (resizing) costs a hot-path indirection plus evidence loss on every resize (hash positions change with the mask). The proposal's "avoid over-provisioning waste" benefit is defeated by its own implementation choice.

**Finding 3 (side discovery) — the shipped 1:1 shape has small futile-probe noise on capacity descents.** fix1024 arms 1.33/run, excess 0.334, floor excursions to ~13 on these workloads: after the hot set drops below capacity, the scan gate (`remain < hotLimit`, 1:1 rooms) reads the stale room occupancy as saturated, the scan locks out, renewal dips, and the governor runs futile raise probes (threshold = max(floor, boundary) is unchanged — the probes are inert). The physical-gate + key-budget shape removes this noise entirely — but only because the 4096-room array provides room headroom, i.e. at the 4× footprint price. Trading 16-36% per-op throughput for ~0.33 excess and ~1.3 futile probes per run is a bad trade; if the noise ever matters, a footprint-neutral fix is a separate experiment.

**Implementation traps (would bite any future implementation of the split).** (1) **Descent deadlock**: the scan gate must stay on the PHYSICAL occupancy — a logical-k gate reads a half-full room set as "saturated" the moment k drops, freezing the scan and blocking newcomers (the first 2-seed run surfaced it directly). (2) **Room-collision budget misfire**: with 4096 rooms, `remain` (active ROOMS) runs ahead of the promoted-key count under collisions, so a room-based budget break truncates the candidate scan while qualifying keys are unvisited (the oracle's coverage read 0.868 instead of 1.000 until the budget was re-based on promoted keys per tide).

**Decision.** Reject the logical-hotLimit controller; `hotLimit` stays a fixed constructor parameter with the current 1:1 beacon sizing and the shipped gate/budget semantics. No Java change.

**Considered options.** (1) **Adaptive logical k (the proposal)** — rejected: oracle ≡ fixed-k on all behavior axes; coverage-only gain is throughput-free by the Java bench; two-dimensional controller risk (ADR-0045/0051/0052 history) with no measurable upside. (2) **Physical 4096 + fixed k (the shape change alone)** — rejected: 4× beacon footprint for the measured 16-36% per-op throughput penalty; the only gains are +0.062 coverage and the removal of small futile-probe noise. (3) **Physical 4096 + static k = max** — equivalent to fix4096: zero noise, full coverage, but the same 64 KB penalty; 1024 remains the measured throughput optimum. (4) **Footprint-neutral descent fix** (keep 16 KB, repair the scan lock on descents) — NOT evaluated here; a separate experiment if the probe noise is ever reported as material.

**Consequences.** The sandbox files are retained as the measurement record (`hotlimit_no_win.py`, `hotlimit_no_win_120.log`, `png/hotlimit_no_win.png`, `debug_oracle.py` — the trap-reproduction scenarios). The side finding (1:1 descent lock → futile probes) is documented here for a future footprint-neutral experiment; it must not be fixed by growing the beacon, and it must not be fixed by the logical-k machinery, which the oracle has shown to be inert.

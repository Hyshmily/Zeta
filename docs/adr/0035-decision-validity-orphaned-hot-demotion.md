# 0035: Decision Validity — Orphaned HOT Demotion on Worker Loss

Takeover in Zeta is implicit re-hashing (`KeyReporterImpl` rebuilds the ring every 50ms and routes past dead nodes); the new owner cold-starts with a global prior (`ZetaBayesianSM`), and a Worker decision is only revoked by its issuing Worker's own COOL broadcast. When a Worker dies or restarts, its CONFIRMED_HOT keys are left with HOT TTLs (1h default) and no one to cool them: the new owner needs confirmCount + HIGH Bayesian confidence to re-confirm, and keys that stop being reported are never re-evaluated at all. We decided that a Worker decision is valid only while its issuing incarnation is alive, and that orphaned entries revert to the ordinary local lifecycle on the read path.

**Decision (Option A + in-place rewrite):** the read path (`HotKeyCache.get`/`getWithSoftExpire` via `ExpireManager.demoteIfDecisionInvalid`) checks the entry's decision stamp against the cluster health view: `decisionNodeId` record absent, Worker not alive (same freshness judgment as the ring/report path — `readyToServe && !stale && heartbeat < timeout`), or current epoch ≠ `decisionEpoch` (restart) → the entry is rewritten in place: `KeyState.HOT → NORMAL`, TTLs reverted to the entry's normal baseline, decision stamp cleared, **value preserved and still served**. No scan — only entries actually read are visited; the predicate is re-verified inside the atomic `compute` so a concurrent fresh broadcast (recovered Worker) is never clobbered. Convergence: first read after invalidity; unread entries still converge at the hard TTL. The background refresh path needs no extra handling — `applyRefreshTask` preserves the demoted NORMAL state.

**Rejected alternatives:** (B) a new "state reset" takeover broadcast message from the new owner — needs a new message type plus acceptance semantics, disproportionate complexity; (C) full O(N) L1 scan on Worker-death events — rejected for cost. The stale-flag level of liveness (`degradeAfterFailures`) was rejected for the predicate: the ring already re-hashes at the freshness timeout, so demotion must use the same judgment to avoid a window where reports route to the new owner while L1 still trusts the dead owner's entries; heartbeat send cadence (1s) vs timeout (10s) already provides 10× intrinsic debounce, and flip-flop under in-place rewrite is free (value stays, ADR-0024 rebroadcast re-promotes within 10s).

**Consequences:** the effective cache lifetime of an orphaned hot key drops from the 1h HOT TTL to the normal TTL (5min default), after which local TopK re-decides — consistent with ADR-0021's graceful degradation ("local TopK drives L1 TTL"). Demotion and local promotion are mutually exclusive within a single read (promotion judges the pre-demotion snapshot), so a demoted entry stays NORMAL for one read and the local TopK re-promotes it on the next read if still hot. Clearing the decision stamp makes the demoted entry a pure local entry, so any subsequent local promotion carries no stale stamp and no demote↔promote oscillation can occur. Epoch ordering (`VersionGuard.shouldSkipForWorker`) already covers acceptance of takeover decisions, and the former `decisionVersionHwm` heartbeat field (once considered as an ordering carrier for a takeover broadcast) was removed as unconsumed. No configuration surface: the behavior is always on.

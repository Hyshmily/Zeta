# ADR-0049: Beacon Decay Sweep Period (4-Tide Hot-Set Memory)

The routing beacon's 2-tide memory (ADR-0038: seed 2 + per-tide halving decay) is fixed by construction, but the sandbox measured it wrong for periodic earners: a key that earns 1 tide and misses 2 is decayed out by its second quiet tide and cold-routed on **every** earn tide (0% hot coverage — the promotion at the earn tide's end serves the NEXT tide, which is quiet). We decided to slow the decay sweep instead of changing the seed or the field width: the halving decay now runs on every other PROMOTED tide, so the memory is 4 tides — earn/miss/miss keys stay hot-routed (100% coverage), drifted keys still leave within 4 non-empty tides, and the SWAR decay identity, the 2+2-bit room layout and the beacon size are untouched. Validated first in the `zeta-tidal-sim` sandbox (`mem_adapt_exp.py`).

**The sweep period.** A deliverer-side sweep clock (`sweepCountdown`, counting down from the period constant `DECAY_PERIOD = 2` — the constant is load-bearing, not documentation) chooses between `decayCounts()` (the existing mask-shift SWAR) and the new `countActiveCounts()` on each scan tide: the skip tide freezes the evidence and reports only the active size via one or-shift + popcount per long (`(word | word >>> 1) & ACTIVE_LANE_MASK` — the lane's bit0 becomes exactly "evidence >= 1", including the evidence-2 case a naive bit0 popcount misses). The clock advances only where the decay gate runs, so empty and sub-minimum tides freeze the sweep clock exactly like they freeze the evidence (ADR-0038). `clear()` resets the clock to 1 (blank-slate contract: the next promoted tide decays).

**The sandbox measurement (`mem_adapt_exp.py`, faithful count→tide→promote→governor port, real request streams).** Hot-routing coverage of tracked hot keys on their own earn tides (cold-start tide excluded):

| workload | M1 (1-tide) | M2 (2-tide, legacy) | M3 (3-tide, seed-3 decrement) | M4 (4-tide, sweep period 2) |
| --- | --- | --- | --- | --- |
| stable (earn every tide) | 100% | 100% | 100% | 100% |
| square (earn1/miss1) | 0% | 100% | 100% | 100% |
| earn1/miss2 | 0% | **0%** | 100% | 100% |
| earn2/miss2 | 52% | **52%** | 100% | 100% |
| earn1/miss3 | 0% | 0% | 0% | 100% |
| 24-seed fuzz (per-key random periods) | 48.5±13.4 | 69.0±12.4 | 91.7±7.0 | 99.9±0.3 |

Drift cost: after the last earn, the stale HOT_A member set survives 2 tides (legacy) vs 3 tides (M4) before its beacon evidence reaches 0 (`mem_adapt_exp.py` eviction: tide 12 vs 13; consistent with the "gone by tide 5" test amendment). The governor's response to the stretched stale window is measured in `gov_interaction.py` (below) — the sweep costs at most one extra walk step and one extra walk verdict, never an unbounded excursion.

**Considered options.** (1) **M3 — seed 3 + decrement decay (3→2→1→0)**: equal coverage for gap-2 earners but worse churn than M4 (re-seeds every earn tide) and it breaks the SWAR halving (saturating decrement cannot be masked across 2-bit lanes) — rejected, M4 keeps the SWAR with the same coverage. (2) **Per-key adaptive memory (renewal-dependent)**: proven meaningless for this problem — gap-2 keys re-promote every cycle and never reach state 3, so their memory is the seed's regardless of renewal history (the sandbox logic, section 3 of the analysis). (3) **M1 — route membership ≥ 2 (1-tide memory)**: catastrophic — even the designed square wave drops to 0% coverage; the "short memory for drift" direction is rejected (drift eviction was already ≤ 2-3 tides; the cost of a lingering zombie is bounded, the cost of a cold-routed earner scales with its volume). (4) **Wider fields (3/4-bit, seeds 4/8)**: beacon grows +50-100% (24/32 KB at hotLimit 1024) for no coverage gain beyond M4 — rejected. (5) **A governor-driven adaptive period**: no — the existing five interacting mechanisms (pacer, floor governor, quiet bypass, flood collapse, incumbent-first) already bound both regimes; the sweep is a single fixed knob, not an operator knob.

**Governor interaction (re-audited, `gov_interaction.py`, corrected sim).** The 4-tide memory stretches the stale tail's residence in `remain`, so every `MoonsTidalForce` parameter was audited — none needed changing. Re-audit note: the first audit ran against a sim governor that predated the ADR-0045 §II refinements (arm-time first step, `STEP_INITIAL` 16, and the rejected mid-walk admit enabled) — its "COLLAPSE@13 → @15" drift reading was an artifact of that stale port. The sim was corrected to the shipped governor (deferred first arm step, `STEP_INITIAL` 8, mid-walk admit removed from `GOV_FIXES`) and the canned scenarios re-run: the 1s square wave, the P1 quiet regime and the P2 stale-flood scenario were M2/M4 identical or bounded (one extra walk step + designed ADMIT), and drift differed only by the verdict path (M4 CRASHED@14 vs M2 CONFIRM@18). ADR-0045 §IV then normalized the skip-tide governor reading to the decay-equivalent basis — after which **all four canned scenarios are M2/M4 bit-identical** (square: ARM→FAILED cycles; quiet: QUIET@19/RE-ENGAGE@37; stale-flood and drift: ARM@11 CONFIRM@15/@18, floor never above the seed): the sweep's routing gain (100% periodic-earner coverage) is delivered with zero governor-behavior delta vs the legacy 2-tide memory. The one code change is a comment fix: `RAISE_ARM_DELAY`'s rationale ("distress visible for at most one tide per pollution wave") was true for the 2-tide memory and is now ~4 tides — the arm delay itself stays 1 because the walk's verdict, not the arm delay, is the noise filter. (Same audit also corrected the sim's stale `STEP_INITIAL` reference — the ADR-0045 §II 16→8 refinement — and the release-stride javadoc's "16 = initial × margin" in `WaveCounter.java`, which still described the pre-refinement value.)

**Consequences.** Per-op routing cost unchanged (1-2 beacon reads, no per-op change). Per-tide deliverer cost: the skip tide swaps the decay pass for an equal-cost popcount pass (same beacon sweep, no per-room loop). The hot-set memory contract changes from 2 to 4 tides: every consumer of the "leaves within 2 tides" statement was updated in `WaveCounter.java` (class doc, beacon field doc, `INIT_COUNT`/`DECAY_SHIFT` docs, `decayCounts()`/`countActiveCounts()` docs, the promote ordering contract, the saturated-branch and incumbent-split comments, and the governor's internal "2-tide" references). The sandbox sim's legacy default (`tidal_sim.py`) is unchanged — it remains the historical record (`STEP_INITIAL` 16, arm-time first step, `fix_mid_walk_admit` switch); `mem_adapt_exp.py`'s `GOV_FIXES` carries the M4 variant AND the current shipped governor (deferred arm, `STEP_INITIAL` 8, no mid-walk admit) so the governor audit runs the real code's machine.

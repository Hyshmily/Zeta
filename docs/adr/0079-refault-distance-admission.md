# Refault Distance Admission for L1 Warming (the `workingset.c` Port)

The kernel-inspired optimization report (§4) proposed porting `mm/workingset.c`'s shadow-entry refault distance to the L1 write path: a key re-fetched after eviction is admitted only if the distance, measured in eviction-clock ticks since its last eviction, would have fit inside the current cache — "it would have survived" as the admission evidence, complementary to TinyLFU's frequency and HeavyKeeper's expelledQueue. This ADR accepts the port in principle, corrects two fail-closed defects in the report's pseudo-design (before the fixes, the report's own "worst case degrades to full admission" safety claim is false), and fixes the rollout plan.

## Status

accepted, implemented (2026-09-25)

## Context

**The loss mode.** Zeta's warming/promotion paths (Worker HOT broadcast, local TopK promotion, `@Preload`) decide *hot*, never *fits*. Scan/traversal traffic is the kernel's documented thrashing shape: average inter-access distance exceeds capacity, every insertion evicts something else, and no eviction policy helps — the only remedy is to not admit keys that cannot survive until their next access. The evidence chain is one neither existing mechanism provides: repeated scan cycles *do* accumulate TinyLFU frequency and HeavyKeeper counts, so scan keys can legitimately beat victims on frequency. Distance — "even with a free slot back then, would you have survived until this visit?" — is the only chain that answers it.

**Code audit (report premises verified).** `HotKeyCache.loadCacheEntry` (`HotKeyCache.java:1450-1499`) is the single choke point for load-path insertions and is unconditional (only the Worker-managed and `VersionGuard` guards refuse). The L1 builder (`ZetaAutoConfiguration.java:437-453`) wires either `maximumWeight` + weigher or `maximumSize`, a variable `Expiry` (hard/soft TTL), and **no** removal or eviction listener — the `ZetaCacheCustomizer` javadoc mentions `removalListener` only as a user extension point. L1 writes are otherwise *not* unified: updates/promotions/demotions across `HotKeyCache`, SWR refreshes (`ExpireManagerImpl`), Worker broadcasts (`DefaultWorkerDecisionHandler`), sync writes (`DefaultSyncDecisionHandler`) and null loads all `compute` into the same cache. The report's "unified entry" claim is therefore corrected to *unified entry of load-path insertions*, and the gate applies only there.

**Defect 1 — slot sentinel.** The pseudo-design stores the raw clock into zero-initialized `shadowSlots`. After days of uptime, a *never-evicted* key reads `dist = clock − 0` — a false large distance — and is rejected; rejection means it is never evicted, so it never gets a shadow: **permanent rejection**. The kernel has no such path: a shadow entry lives in the evicted page's own slot, and "no shadow entry" is an explicit branch that activates normally. Fix: slots store `(clock & 0xFFFFFFFFL) + 1`; `0` means *no evidence → admit*.

**Defect 2 — clock purity.** Zeta's L1 expires by variable `Expiry`, so `EXPIRED` is the *common* removal cause; `compute` replacements are `REPLACED`; cross-instance invalidations are `EXPLICIT` (`DefaultSyncDecisionHandler.java:228`). Counting any of them advances the clock at TTL cadence, distances systematically overestimate, and the gate mass-rejects — fail-closed, strictly worse than the status quo. Fix: the clock counts **only `RemovalCause.SIZE`** (capacity-driven evictions, count- or weight-based). After the fix, the residual errors are all in the optimistic direction — bucket collision overwrites a shadow with a newer stamp → small dist → admit; 32-bit lap → small dist → admit; listener batching delivers the notification late → small dist → admit — so the report's original fail-open claim holds again.

**Value is deployment-conditional.** The gate only bites where `maximumSize`/`maximumWeight` actually binds; generous-capacity deployments see identical behavior plus the table's fixed cost. The rollout therefore proves the loss mode on real traffic before enforcement is enabled — the ADR-0078 playbook.

## Decision

- **Clock.** `AtomicLong evictionClock`, incremented only from removal notifications with `cause == RemovalCause.SIZE`. `EXPIRED`/`REPLACED`/`EXPLICIT`/`COLLECTED` never advance it. One line of cause filtering is the difference between a distance signal and a TTL shadow. `AtomicLong` (not `volatile` `++`): removal notifications can arrive from both maintenance and writer threads. 32-bit working width with masked subtraction (`(clock − shadow) & 0xFFFFFFFFL`, `workingset.c:511-512`); lap errors are accepted as optimistic per the kernel's own analysis (`:495-510`).
- **Shadow table.** An independent power-of-two `long[] shadowSlots`, sized ≥ **8× effective entry capacity** (2^16 slots = 512 KiB covers cap ≤ 8k entries), mask-indexed. The stamp writes `(clock & 0xFFFFFFFF) + 1` — the `+1` reserves `0` as empty — through a release-mode `VarHandle` array access. Not aliased onto HeavyKeeper's geometry: the sketch's width serves the precision model (ADR-0014) and can be orders away from the capacity-derived size; the shadow table's correct size is a function of *cache capacity*, not sketch precision. The 8× rule carries two justifications: the report's own (a shadow older than `cap` evictions would be rejected anyway), and collision survival — `P(true shadow intact) ≈ exp(−cap/table)`: at table = 8× cap, ≈88% of decisions read the true shadow; at table ≈ cap the gate degenerates into noise. Auto-derived tables clamp to [2^8, 2^18] (a sub-density table degrades optimistically — collision-driven admits); explicit `refault-shadow-bits` up to 2^24 is an operator's choice. Capacity is measured in **entries** on both sides of the comparison and is the **static configured bound** (`max-size`, or `refault-capacity-entries` in weight mode) — the value Caffeine actually enforces under pressure, i.e. the kernel's working-set-size term. An EWMA of `cache.estimatedSize()` was considered and dropped: the gate has no cache back-reference, and the enforced bound (not the transient fill level) is the pressure-relevant quantity. A non-positive effective capacity (weight mode with `max-size` zeroed and no override) **fails fast at construction**: with no capacity term every evidenced distance exceeds it and the gate mass-rejects — the one direction the port must never lean (post-adoption fix; the original "optimistic, never pessimistic" claim was false).
- **Residency-end stamps (implementation refinement over the report).** The report's "on eviction, stamp" becomes cause-differentiated, because Zeta's solo-flight cycle needs the anchor refresh the kernel gets for free by re-evicting inactive pages: `SIZE` (capacity eviction) advances the clock **then** stamps — the only clock input, **except a solo-flight entry's own SIZE eviction**, which stamps at the current clock without advancing (post-adoption fix: the gate's own churn is not residency turnover, and counting it would feed the reject rate back into the clock every distance is measured against — a sustained scan flood would inflate all distances until the gate rejected everything it had ever seen leave); `EXPIRED` (own TTL end, including every solo-flight cycle's end) stamps **without** advancing the clock, so the next refault measures evictions since that cycle's end and the reject loop is **self-correcting** — sustained pressure keeps re-rejecting, a stopped flood re-admits (without this, a rejected key's stale anchor would freeze its distance above capacity forever: permanent rejection); `EXPLICIT` (cross-instance invalidation, the kernel's truncate) **clears** the slot — freshly written data re-admits as cold; `REPLACED`/`COLLECTED` leave evidence untouched. Residual errors stay optimistic: bucket collision (newer stamp → small dist), 32-bit lap (masked subtraction reads laps as small churn), listener delivery lag — with one documented pessimistic residual: notification delivery is unordered across threads, so an `EXPLICIT` clear can lose to a same-key stamp whose eviction predates it; the evidence re-appears for at most one reject cycle before the next anchor re-stamp self-corrects.
- **Gate.** Inside `loadCacheEntry`'s `compute` the gate consults exactly the re-admission decisions: `existing == null` (fresh insert) **or** `existing` is a logically-expired `CacheEntry` (dead residency — without this the update path would rebuild a solo-flight or expired entry at full TTL, silently promoting it back). A fresh resident entry (concurrent-load race) is residency continuation and is never distance-refused. Decision: `slot == 0 → admit` (no evidence, the cold-key rule); else `dist = (clock − (slot−1)) & 0xFFFFFFFFL`; `dist ≤ capacityEntries → admit`; else **reject**. The distance math inside the bin lock is a masked subtract and a compare; SingleFlight and Worker reporting are unaffected — only residency scope changes.
- **Solo-flight entries.** On a reject the loaded value is stored via the normal entry machinery with hard TTL = `refault-reject-ttl-ms` (default 200ms), soft TTL 0, NORMAL state, and the **solo-flight flag** set (a bit in `CacheEntry.packedState`'s reserved range, carried across draft copies — post-adoption fix: the flag lets the clock/shadow keeper distinguish the gate's own churn from true turnover on a `SIZE` removal; the original "no CacheEntry model change" made the reject rate a clock input). Version identity follows the same stamped/fail-open rules as a normal insert. The value is served to the caller as any load result, so rapid re-reads within the window coalesce through L1 instead of hammering the backend; the entry's end (EXPIRED, or the SIZE eviction of its churn) re-stamps the anchor (see residency-end stamps), which is what makes the reject loop converge.
- **Exemption list** (write paths that bypass the gate, each with a reason): Worker-managed HOT/COOL broadcasts (Worker decision evidence outranks distance; the `isWorkerManaged` guard already prevents overwrite churn), `@Preload` (operator intent), cross-instance sync writes (consistency semantics, not warming), null/`NullValue` loads (governed by §13.3's negative budget, not this gate). Residency updates are exempted structurally by the `existing != null` branch above.
- **Modes and default.** `zeta.local.cache.refault-admission = off | shadow | on` (the knobs live in the L1 `CacheConfig` block beside `max-size`), **default `shadow`** — the full machinery (listener, table, decision) runs and the gauges expose what `on` would do, but nothing is enforced; the same conservatism as ADR-0078. The per-load shadow cost is two atomic reads and one masked subtract. Companion knobs: `refault-reject-ttl-ms` (solo-flight hard TTL, default 200), `refault-capacity-entries` (weight-mode capacity override), `refault-shadow-bits` (0 = auto-derive).
- **Gauges** (registered only when the gate is active, mode != off): `zeta.l1.refault.admit.total`, `.reject.total` (cumulative verdicts; shadow-mode rejects are the would-reject rate), `.distance` (latest evidence-backed distance, −1 = no evidence), `.capacity` (the static bound), and `.clock.rate` — the capacity-eviction rate (evictions/sec, EWMA over scrapes), independently valuable as the scan-pressure alarm the cache never had.
- **Validation.** The derived table size and the mode enum fail fast at binding like ADR-0068's bounds. Unit tests must cover: the sentinel (never-evicted key admitted after the clock advanced), SIZE-only filtering (EXPIRED/REPLACED/EXPLICIT storms leave the clock untouched), wrap-around, collision overwrite (optimistic direction), a TTL-only workload (no SIZE events → gate admits everything), and residency updates never refused.

## Considered Options

- **Count all removal causes** (the report's literal "每次驱逐 +1"): rejected — TTL cadence dominates the clock and the gate mass-rejects; fail-closed.
- **Stamp on SIZE only** (the report's literal "on eviction, stamp"): rejected — a rejected key's residency ends with EXPIRED (the solo-flight's own TTL), which would never refresh its anchor, freezing its distance above capacity: permanent rejection. The EXPIRED re-stamp (no clock advance) makes the reject loop self-correcting.
- **Store the raw clock in zero-initialized slots**: rejected — permanent rejection of never-evicted keys; the sentinel encoding fixes it.
- **Alias the shadow table onto HeavyKeeper's width**: rejected — sketch geometry serves the precision model (ADR-0014) and can be orders away from the capacity-derived size; also forfeits the power-of-two mask.
- **Gate all L1 write paths** (a true "unified entry"): rejected — Worker broadcast/preload/sync carry their own evidence or consistency semantics; gating them changes features, not cache hygiene. The load path is where "should this freshly fetched value live here" is genuinely open.
- **Pure read-through for rejects**: rejected as default — it amplifies backend load precisely during scan floods; short-TTL coalescing keeps the single-flight benefit.
- **Ship `on` from day one**: rejected — the ADR-0077 lesson; shadow gauges first, enforcement is an operator flip backed by the evidence trail.

## Consequences

1. Default `shadow` is admission-identical to `off` (everything is admitted) while the machinery runs: a fixed 512 KiB table (2^16 slots), one atomic increment per SIZE eviction, two atomic reads per load-path insert. The gauges are the evidence trail.
2. On `on`: scan/traversal keys stop churning L1 residency and the true working set survives push-warming storms. Acceptance is a hit-rate A/B under the demo-app k6 scan-flood scenario (gate on vs off) on a capacity-bound configuration.
3. Residual error directions after the fixes are all optimistic (collision, lap, late delivery, stale shadow read → admit): worst case equals today's unconditional admission — the report's original safety claim, now actually true.
4. `zeta.l1.refault.clock.rate` is a new first-class signal: sustained capacity-eviction pressure is visible and alertable even while the gate is in shadow.
5. Composition path: §13.1's DAMON quota water-mark ("worth it within quota") and §13.3's negative budget gate the same `loadCacheEntry` choke point — one choke point, three independent evidence chains (distance, quota, negative-budget). Land them independently; none changes another's contract.
6. **Post-adoption fixes (2026-09-26 audit round).** (a) The solo-flight flag on `CacheEntry.packedState` (bit 58): a rejected flood's solo-flight entries are evicted by SIZE as window churn, and counting them advanced the clock with the reject rate itself — a feedback loop that inflated every distance until the gate mass-rejected its own history (the fail-closed direction); solo-flight SIZE now re-stamps without advancing. (b) Non-positive effective capacity fails fast at construction, replacing the false "optimistic, never pessimistic" claim for weight-mode deployments without the override. (c) The `.distance` gauge write moved from a volatile store to release/acquire: a volatile store per miss (an mfence on x86) put a cross-core invalidation on the exact path a scan flood hammers. (d) The unordered-delivery pessimistic residual is documented (above) instead of serialized away — serializing the keeper cannot fix a reorder that happens upstream in the delivery executor.

# Reporter Feed-Loop Flush Cadence (the `damon_feed_loop_next_input` Port)

The kernel-inspired optimization report (§3) proposed porting DAMON's 20-line monitoring-intervals feedback loop (`damon_feed_loop_next_input`, `mm/damon/core.c:2751-2780`) to three Zeta knobs. We adopted **one** — the reporter flush cadence — rejected the other two on architectural grounds, and shipped the port behind a shadow-mode default so the trajectory is observed before it is applied. The report's own §0/§15 had already dropped the weakest usage point; this ADR records the full verdict and the composition rules with the WaveCounter tide machinery.

## Status

accepted (2026-09-25)

## Context

`KeyReporterImpl` flushed on a static base interval (`zeta.local.report-interval-ms`, default 50ms) wired as the WaveCounter tide base. Under a 10x traffic swing the static cadence is wrong at both ends: near-idle instances pay a full routing + AMQP publish round per nearly-empty batch, while heavily loaded instances would rather amortize per-message overhead — the knobs DAMON designed the feed loop for. The three proposed usage points, re-audited against the actual code:

1. **Worker aggregation window — rejected.** The Worker is *push-driven* (RabbitMQ → `SlidingWindowDetector`); there is no polling period to stretch, which is the idle cost DAMON's `aggr_interval` tuning exists to minimize. Worse, the sliding window duration is the *semantic time unit* of the Bayesian state machine — `confirmCount`, `coolWindows`, pre-cool grace and the ADR-0051/0058/0059 retreat machinery all count windows, so re-tuning the window online makes accumulated evidence non-comparable across regimes. "K candidates per window" as a *goal* is also normatively backwards: the correct candidate count is what the traffic distribution produces.
2. **Reporter flush interval — adopted (this ADR).** The flush clock IS the WaveCounter tide clock (`deliverIntervalMs = reportIntervalMs`; the flush-clock discharge was removed long ago), so the report's own "does not cover the tide path" fence was self-contradictory — resolved here by making the tuner *own the base* that the existing tide adaptations act around (see Decision). The report path's `opMaxCount` is a 100k safety valve, so the flush is purely clock-driven and the batch size is a clean plant signal.
3. **`WaveCounter.opMaxCount` — rejected.** 128 is a *measured design decision, not an operator knob* (16-thread 64/128 sweep knee), structurally coupled to `LOCAL_CAPACITY/2`, the bitmap sweep and the tide cadence. Making it tunable means a shared mutable read on the hottest path — the codebase engineered a last-key short-circuit specifically to avoid a ~3-10ns beacon read (ADR-0043/0048). The low-traffic case is already absorbed by the tide draining (batches never reach 128) and the high-traffic case sits at the knee. The doc's "+1 effort" estimate ignored all of this.

The `balance_dirty_pages` quota-pause coupling supplement (batch goal × rate = pause) is acknowledged as the right *next* step but is deferred: it wants the §2 BBR baseline as a shared `task_ratelimit` signal, and shipping both couplings at once would leave two moving baselines and no reference point. (ADR-0077's boundary still holds: the tuner moves the *cadence upstream*, never the dispatcher's queue or the BBR budget.)

## Decision

- **`util/FeedLoop.nextInput(lastInput, scoreBp, minInput)`** — a faithful, stateless port of the kernel function: additive compensation `last ± last×|score−goal|/goal` (algebraically identical to the report's multiplicative transcription), the `score ≥ 2×goal → minInput` overshoot cliff, the overflow guards (kernel's `last < ULONG_MAX/diff` reordering and the `ULONG_MAX` saturation), and `minInput` as a *parameter* — the kernel's hardcoded `10000` is a **microsecond** floor; taken literally into Zeta's milliseconds it would be a 10-second floor. The single-step change is bounded by construction (≤2x below the cliff), which is the kernel's effective `[0.5x, 2x]` step limit; callers clamp the result into their own `[min, max]` window.
- **`reporting/impl/ReportFeedLoop`** — the tuning policy around the pure function: goal `N = zeta.local.report-interval-target-batch` keys per flush, score = two-window-averaged batch size in bp of the goal (the kernel's noise filter), result clamped to `[report-interval-min-ms, report-interval-max-ms]` (the ceiling is the detection-lag bound). **Censoring is the caller's duty**: only flushes that actually reached the routing stage are sampled — empty snapshots, no-alive-Worker drops and BBR gate drops return upstream of the sampling point (the kernel has no analog; its sampler always completes its round, Zeta must not learn from censored cycles).
- **`WaveCounter.adjustDeliverIntervalMs(long)`** — the tide base becomes volatile and adjustable (clamped up to `EARLY_TIDE_MIN_INTERVAL_MS` so the governor's flood-rate normalization keeps a valid divisor). Composition rule: the tuner **owns the base**; backlog pressure still compresses non-empty tides from the base to the floor, and the empty-tide ladder still stretches idle cycles to 2x the base — one controller per signal, all expressed through one number. Effect lands at the *next* scheduled tide (one fire of lag by design: the batch just flushed accumulated under the previous base, which keeps the `lastInput → score → nextInput` sequence well-defined).
- **Modes and default.** `zeta.local.report-interval-tuning = off | shadow | on`, **default `shadow`** — the tuner computes and exposes everything but applies nothing, so `zeta.reporter.feedloop.interval` shows on real traffic what `on` would do before an operator flips the switch. This is the same conservatism that rejected ADR-0077's auto-tuning.
- **Gauges** (registered only when the tuner exists): `zeta.reporter.feedloop.interval` (base interval, the trajectory), `.score` (bp, 10000 == on target), `.batch` (averaged keys per flush).

## Considered Options

- **Adopt usage point 1 (Worker window tuning):** rejected — push-driven Worker has no idle sampling cost to reclaim, and the window is the state machine's unit of evidence; see Context.
- **Adopt usage point 3 (adaptive `opMaxCount`):** rejected — hot-path volatility, measured-default philosophy, negligible worst-case cost; see Context. If ever revisited: a plain (non-volatile) int written by the deliverer and racily read by writers is the only acceptable shape, and it must be tide-boundary-adapted, not feed-looped.
- **Port `min_input = 10000` literally:** rejected — unit trap (µs vs ms); the parameterized floor keeps the "compensation never degenerates to zero" role while re-deriving the value from Zeta's own scheduler bound.
- **Ship the `balance_dirty_pages` quota-pause coupling in the same pass:** deferred — one moving baseline at a time; the deterministic `interval = clamp(batch/rate, min, max)` half needs §2's `balancedInFlight` and the `min_pause = max_pause/2` stability band ported with it.

## Consequences

1. The report flush cadence is self-tuning only when an operator opts into `on`; until then the default behavior is byte-identical to before (tide base static at `report-interval-ms`), with the shadow gauges as the evidence trail.
2. `maxIntervalMs` scales the empty-tide ladder with it: an idle instance's worst-case flush gap becomes 2x the tuned base (bounded by `report-interval-max-ms`, default 1000ms → 2s idle gap). A brand-new hot key after a long idle period waits up to that gap before its first report — the detection-lag price of the power saving, capped by config.
3. Gate-dropped and censored cycles produce no tuner samples by design; under sustained BBR throttling the cadence loop goes quiet and the pipeline is governed by ADR-0011 alone. The two controllers are intentionally not coupled yet (see the deferred supplement).
4. The `zeta.local.report-interval-*` config family is validated at tuner construction (`max >= min`, positive goal) and fails fast at binding time like ADR-0068's bounds.

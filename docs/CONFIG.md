### Core (`zeta.local.*`)

> **Design note:** The app-side HeavyKeeper uses wider (50k configured, auto-aligned up to the nearest power of two — 65,536 by default — so bucket indexing takes the mask fast path) but shallower (depth 5) sketch dimensions with slightly slower decay (0.92). A wider sketch reduces fingerprint-collision probability on single-key inserts (the app path). Shallower depth is acceptable because the app only needs a fast _heuristic_ for local promotion — it does not make authoritative HOT/COOL decisions.

> **Connection isolation:** Heartbeats (producer + PING/PONG verification) use a **dedicated `CachingConnectionFactory`** (`zetaHeartbeatConnectionFactory`) and **dedicated `RabbitTemplate`** (`zetaVerifyRabbitTemplate` / `zetaHeartbeatRabbitTemplate`), completely isolated from the data-plane connection shared by reports, broadcasts, and sync. This prevents data-plane congestion or broker flow-control from delaying heartbeat delivery — the heartbeat TCP connection has its own channel pool independent of data-plane traffic. One extra TCP connection per node is the cost. The dedicated factory inherits the same `spring.rabbitmq.*` settings (credentials, virtual host, `ssl.*`) as the data-plane factory, so TLS configuration is shared. The dedicated factory (and its `@Primary` marking) is created only when `zeta.worker-listener.enabled=true` or `zeta.worker.enabled=true` — report/sync-only applications get no extra `ConnectionFactory`. The Worker's control-plane template additionally **pre-declares the heartbeat exchange on this connection** before any publisher can use it, so the first publish cannot race the declaration — see the declaration-ordering notes under `zeta.worker-listener.*`.

| `zeta.local.circuit-breaker.include-exceptions`            | `[]`    | Exception class names (fully qualified) that SHOULD trip the breaker (empty = all) |

The circuit breaker wraps `SingleFlight.load()` — when open, `load()` returns `Optional.empty()` immediately without executing the supplier. The calling `HotKeyCache.get()` then falls back to returning any stale L1 entry whose **hard TTL has not expired** (soft-expired, hard-valid entries; a hard-expired entry is never served as stale — the hard TTL contract is not bypassed, see CONTEXT.md "Expire"). Only enable when your cache-load suppliers (database queries, remote API calls) are prone to cascading failures.

> **Default is intentionally `false`.** Enabling the breaker by default would change the read path for every user (stale-serve fallback on open), so the default stays off and flipping it is a deliberate opt-in. Changing the default to `true` is reserved for a future major version.

**State machine:** CLOSED → OPEN → HALF_OPEN → CLOSED. In CLOSED state, a sliding-window tracks failure rate. When the rate exceeds `fail-threshold` and volume meets `request-volume-threshold`, the breaker opens. After `single-test-interval-ms`, one probe request enters HALF_OPEN. It requires `consecutive-success-threshold` consecutive successes to close — any failure in HALF_OPEN returns immediately to OPEN. This anti-flapping design is inspired by the `neural-circuitbreaker` project.

**Exception filtering:** When `exclude-exceptions` is non-empty, exceptions matching these types (or their `cause`) are treated as success and never trip the breaker. When `include-exceptions` is non-empty, ONLY the listed exception types trip the breaker — all others are ignored. For example, `IllegalArgumentException` is a client error and should not open the circuit.

> **ℹ️ Startup order** — `zeta.heartbeat.exchange`, `zeta.send.exchange` (App side requires `worker-listener.enabled=true`) and `zeta.reportToWorker.exchange` are each declared by **both the App and the Worker** with identical arguments (durable, not auto-delete); there is therefore **no startup-order requirement** between App and Worker, and a Worker starting first does not leave the health ring permanently empty.

> **ℹ️ Declaration ordering — heartbeat exchange** — the heartbeat exchange is **pre-declared on the control-plane connection before that connection is used for publishing** (`WorkerAutoConfiguration#heartbeatRabbitTemplate` runs an idempotent `exchangeDeclare` through the template's own `execute`). Because every heartbeat and every fast-lane rule-gossip publish goes through that single template instance, the ordering follows from dependency injection rather than from a timing assumption — a cold cluster (empty broker) no longer logs `NOT_FOUND - no exchange 'zeta.heartbeat.exchange'` on its first Worker. The declaration is durable and idempotent, so it also satisfies the App side. See [ADR-0010](adr/0010-epoch-driven-heartbeat.md).

> **ℹ️ Remaining cold-start `NOT_FOUND`** — for everything else (report / broadcast / sync exchanges and queues) declarations are still issued lazily by Spring Boot's `RabbitAdmin` when a connection is created. A one-off `NOT_FOUND` can therefore still appear in the cold-start window: a failure in that declaration pass aborts the remaining declarations, and a concurrently created second connection skips the pass entirely — the first bind/publish on it then gets a 404. That error is channel-scoped, affects a single operation, and self-heals when the next connection re-runs the declarations. **Judge recovery by whether the App-side `ClusterHealthView` / consistent-hash ring becomes non-empty within a few heartbeat periods**, not by whether the 404 recurs; if it does recur, verify the exchange names match on both sides (`zeta.worker.messaging.heartbeat-exchange` vs `zeta.local.heartbeat.exchange-name`).

> **⚠️ Do not register a second `AmqpAdmin`** — Boot's `RabbitAutoConfiguration#amqpAdmin` is guarded by `@ConditionalOnMissingBean` on its **return type** (`AmqpAdmin`), and `RabbitAdmin` _is_ an `AmqpAdmin`. Any admin Zeta registered of its own would therefore silently switch Boot's off and leave every data-plane exchange, queue and binding undeclared — with no error to point at it. The heartbeat exchange is declared from the publishing template precisely to avoid this.

> **ℹ️ Shared-broker appName isolation (ADR-0068)** — every HOT/COOL broadcast carries an `appName` header, and the App-side listener drops decisions whose `appName` differs from its own `zeta.local.app-name` (the fanout exchange ignores the routing key, so on a shared broker every bound queue receives every app's decisions). Messages **without** the header (pre-1.1.58 Workers, rolling upgrade) are always processed. Keep the Worker's `zeta.worker.routing.app-name` equal to the app's `zeta.local.app-name` — a mismatch silently discards decisions (visible at DEBUG). The `zeta.sync.exchange` fanout has the same shape but lower impact (foreign INVALIDATEs are no-ops for unrelated keys); it is not filtered yet.

> **⚠️ IMPACT when disabled:** Without `worker-listener.enabled=true`, the App does not consume Worker heartbeats → `ClusterHealthView` records stay empty → `getAliveWorkerIds()` returns empty → Reporter `routeNode()` returns `null` → all report batches are **silently dropped**. The Worker never receives any data and never broadcasts HOT/COOL decisions. This is the most common configuration error in deployments with a Worker cluster.

## Security

All RabbitMQ connections — the data plane (report, sync, broadcast) and the dedicated control-plane heartbeat factory (`zetaHeartbeatConnectionFactory`) — use plain AMQP connections by default. In production, configure TLS via Spring Boot's `spring.rabbitmq.ssl.*`; the heartbeat factory inherits the same settings, so both planes are covered by a single configuration:

```yaml
spring:
  rabbitmq:
    ssl:
      enabled: true
      key-store: classpath:client.p12
      key-store-password: changeit
      trust-store: classpath:truststore.jks
      trust-store-password: changeit
```

See [Spring Boot RabbitMQ SSL docs](https://docs.spring.io/spring-boot/reference/messaging/amqp.html#page-title) for details. Note: `spring.rabbitmq.ssl.bundle` is not supported by the heartbeat factory — use the `key-store` / `trust-store` properties above.

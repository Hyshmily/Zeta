# Zeta Domain Glossary

## Core Concepts

- **Hot Key** — A cache key with abnormally high access frequency. Ambiguous term; use **Local-Hot** (this instance's detector) or **Cluster-Hot** (a live Worker lease) when precision matters. Neither term implies a TTL change.
- **Local-Hot** — A key whose frequency exceeds the HeavyKeeper TopK threshold on this App instance. It drives local keep-warm scheduling and observability; it never rewrites an entry. `HotKeyDetector` is the sole local source.
- **Cluster-Hot** — A key holding a live `HeatLease` granted by a Worker HOT decision. It permits cluster-scoped spending (optional prewarm, business `onHot`), not a TTL change or a cache-entry state.
- **Admission Event** — The one-time notification emitted when a key newly enters the local TopK. It offers the resident entry to `KeepWarm`; it no longer rewrites the entry or changes a TTL. A plain read does not probe TopK membership.
- **Cacheability (loader)** — The `CacheLoader.isCacheable(value)` verdict: whether the engine may store a value it obtained on the loader's behalf. A declined value is still served and still counts toward detection; only the L1 store is skipped. It is not a per-call bypass and not a global rule — an explicit `put` never consults it.
- **Warm Policy** — `ResolvedNamespacePolicy`: which heat signal may prewarm a missing entry, which may renew a resident one, and which namespace-scoped loader may supply the value. Declared through `WarmRegistry` (from a `ZetaWarmConfigurer`) or the annotations, resolved by `NamespacePolicyRegistry` as YAML override > programmatic > annotation > global, and frozen into an immutable snapshot at startup. Global prewarm and keep-warm default to `OFF`: registering a loader does not opt a namespace into spending background loads, and `softTtl` never switches renewal on.

- **Key Format** — `KeyFormat` (`TYPED`/`PLAIN`) and its declaration vocabulary `KeyFormat.Option` (`INHERIT`/`TYPED`/`PLAIN`), mirroring `HeatTrigger`/`HeatTrigger.Option`. The format is a namespace fact: `TYPED` is `cache + '\u0000' + DefaultKey`; `PLAIN` is `cache + ':' + value` and requires one scalar key type per namespace. A method that names its own `cache` does not inherit the class's format or type; a method that repeats the class cache name does inherit it.

- **Warm Loader** — The one background source of a namespace: either a `ZetaWarmConfigurer` declaration or an `@ZetaCached(selfWarmLoader = true)` method. A namespace has at most one; a second declaration fails startup. `KeyEncoding.Decoder` inverts the physical key for that method only, never for the namespace as a whole.

- **Warm Registry** — `WarmRegistry`: the startup-only builder a `ZetaWarmConfigurer` receives. One namespace has one physical prefix derived from its resolved format; omitting `format(...)` inherits the annotation's format (or the global default when no annotation declared it), and `namespaceRaw` binds a loader that owns the physical key without locking a scalar type.

- **Frozen Policy Snapshot** — `NamespacePolicyRegistry.validateAndFreeze()` resolves every known namespace once and publishes one immutable `FrozenSnapshot` holding the prefix map, the default policy and the keep-warm aggregate. After freeze, `resolve(key)` is one prefix read and one map lookup, and any later registration is a startup error.

- **Decision Skip Reason** — `DecisionSkipReason`: `VERSION_STALE` (the resident stamp already outranks the incoming decision), `GHOST_COOL` (a cross-node COOL while a live owner still routes to the key), or `COVERED_BY_NEWER_DECISION` (a later decision in the same batch superseded it). One vocabulary covers both HOT and COOL skip hooks.

- **Namespace Keys** — `NamespaceKeys`: the plan-time registry of each namespace's `KeyFormat` and locked PLAIN key type. It is written while beans are proxied and read by the facade, separately from the warm registry frozen at `SmartInitializingSingleton`.
- **Heat Trigger** — `HeatTrigger`: `OFF` / `LOCAL` / `CLUSTER` / `ANY`. It selects the signal a warming action accepts; it is not a TTL or a cache state.
- **TTL Declaration** — The one vocabulary every TTL attribute shares: `0` inherits the configured default, `-1` disables a soft window (a hard TTL has no "off" state, so `-1` inherits there), every positive value is used exactly as written, and `Long.MAX_VALUE` means never expires. Any other negative is a configuration error. Resolution happens once, at the layer that owns the configuration; an entry only stores resolved durations.
- **TTL Contract** — `TtlContract`: the normal hard/soft baselines one namespace declares, plus whether the baseline is dynamic. Registered by the annotation layer in `NamespacePolicyRegistry`; a namespace whose declarations disagree becomes non-prewarmable rather than guessing.
- **Strict Hard TTL** — The engine's hard bound is absolute: no path moves `hardExpireAtMs` later than the duration it was computed from. Jitter only subtracts, and a failed hard renewal leaves every deadline untouched.
- **Heat Lease** — `HeatLease`: a `DecisionStamp` plus the observation time. A HOT lease permits cluster spending; a COOL tombstone orders a late HOT. It carries no value and no TTL.
- **Keep-Warm** — A local hard renewal: before the entry's soft or hard deadline, load a fresh value and re-arm the entry's own declared hard/soft durations. It never extends the old value's life, never broadcasts, and never records a read.
- **Prewarm** — A cold-node load of a missing entry through the namespace's declared loader and static TTL. It refuses a dynamic/ambiguous namespace instead of guessing a lifetime.
- **Local-Read Gate** — A cluster-triggered renewal requires a real read observed on this instance since the warm cycle began. Local heat is its own evidence. A lost COOL therefore cannot cause infinite background reloads.

## Data Plane

- **CacheEntry** — The value, its `dataVersion`, and the caller's resolved hard/soft TTL and absolute deadlines. No heat state, decision stamp or normal/hot dual baseline exists on the entry.
- **NORMAL / HOT / COOL entry states** — Removed. The data plane has no per-entry heat state. `NORMAL` in older documentation maps to "an ordinary resident"; `HOT`/`COOL` are now heat-lease events only.

- **WorkerDecision** — The typed App-side view of a Worker broadcast: `(id, cacheKey, DecisionStamp)`. `DecisionStamp.kind()` is `HOT` / `COOL`; it is the one operation field, so a second type field cannot disagree with the lease. The AMQP body and headers stay inside `WorkerDecision.from`.
- **HeatDirectory** — The cluster lease table: `grant`/`revoke` with decision-version, epoch, incarnation and ghost-COOL guards; a short COOL tombstone preserves ordering after a revoke. It owns no value and no TTL. A grant or revoke that replaces a dead lease returns it, so the caller emits the old `onCool` before the new `onHot`.
- **HotKeyHandler** — The one replaceable HOT/COOL action. The default HOT action submits an asynchronous prewarm; the default COOL action has no data-plane side effect. It runs on the ordered dispatcher and must not block.
- **HotKeyListener** — Best-effort observers of applied and skipped decisions and of passive lease endings. A lost COOL is not replayed, so safety-critical business state must carry its own timeout.
- **HotKeyContext** — The guarded operations plus the applied decision's read-only facts (`decision()`, `isNewlyHot()`) handed to `HotKeyHandler`: physical key, normalized `namespace()`, entry snapshot and `hasLiveEntry()`, the two heat queries, asynchronous prewarm, `armKeepWarm()` and cold-judged renewal cancellation. One context belongs to one decision; it never exposes a TTL rewrite, a write handle or the namespace loader.
- **Logical Namespace** — The bare namespace name a key belongs to: `users` for both `users\u0000u-1` (TYPED) and `users:u-1` (PLAIN), produced by `CacheKeysPolicy.logicalNamespaceOf`. It is the only form business code compares; the physical prefix (`namespaceOf`/`physicalPrefixOf`) keeps its delimiter and is reserved for registries keyed by prefix.
- **EntryView** — The read-only entry snapshot handed to `SyncPolicy` and `HotKeyContext`: value, data version, soft/hard expiry timestamps and the two expiry predicates. It is advisory; the guarded write path re-checks every version and tombstone.
- **SyncEvent** — The policy/hook view of one sync message: a key operation (INVALIDATE/REFRESH/PUT), a table-wide clear, or a prefix clear with its raw prefix. It carries no payload and no internal batch structure; `namespace()`/`affectsNamespace()` answer namespace questions for all three shapes without the caller parsing `\u0000` or `:`.
- **SyncPolicy** — The pure decision layer for sync: `admit(SyncEvent, EntryView)` before a PUT decode or REFRESH load, and `settle(SyncEvent, Object, EntryView)` after a value is resolved. It never receives a write context or a `Batch`; the framework owns every apply and terminal hook.
- **SyncHook** — The terminal observer for sync: `afterValueApplied`, `afterValueDegraded` (a value event the framework applied as a local invalidation, with the value-side reason), `afterInvalidate` (an applied peer INVALIDATE), `afterClear` (one per granted clear batch, carrying every effective event) and `onSkipped(SyncEvent, SyncSkipReason)`. Hooks run only on the ordered dispatcher; the rejection fallback fires none.
- **Batch** — A granted sync batch, sealed by shape. `Batch.Value` is a non-clear batch reduced to its effective message and carries `messages`, `winner`, every covered single-key message (PUT/REFRESH/INVALIDATE) and `coveredInvalidate` (the highest covered INVALIDATE); `allowSoftExpire()` is derived from them. `Batch.Clear` keeps every table-wide and prefix clear and has no winner: `DefaultSyncContext` applies them in one sweep. `Batch` is internal to the applier; the policy sees only `SyncEvent`.
- **Decision Validity** — A cluster lease is valid only while its issuing Worker incarnation is alive: `HeatDirectory` checks the Worker's ID and epoch on every `isClusterHot` query and lazily removes an invalid lease with `INCARNATION_DEAD`. The cache entry is untouched; the lease's absence only removes cluster-scoped permission.
- **Local-Read Gate** — A cluster-triggered renewal requires a real read observed on this instance since the warm cycle began. The access-counter tide supplies the keys without adding a read-path probe. Local heat is its own evidence.

## Components

- **App** — The user's Spring Boot application that pulls `zeta` as a dependency. Runs local L1 (Caffeine), local TopK, and the Reporter-to-Worker AMQP link. The library ships no data-access client: callers supply readers, loaders and (optionally) a cluster loader.
- **Worker** — Standalone Spring Boot application (`zeta-worker`). Consumes App reports via AMQP, runs a sliding-window detector and a rule-based promotion/cooling engine (no HeavyKeeper/TopK sketch), emits HOT/COOL decisions back to Apps via broadcast. Published as a separate module, never deployed to Maven Central.
- **Capacity Relief** — The Worker detector's behavior at the tracked-key cap (`zeta.worker.max-tracked-keys`). A new key first asks the sampler for one locked pass over 32 live windows and reclaims every one whose last write is more than a full window old — the slice-aligned boundary the read path uses, so each already sums to zero for every reader and no count is lost. A pass that finds none opens the **Saturation Window** for the arrivals behind it but still admits its own key from the **Hard Headroom**; only a full hard ledger that also finds nothing idle rejects it, and the rejection arms the next periodic scan with the window-length threshold, bounding the lockout to one scan interval. The pass walks a round-robin sweep hand over the table instead of restarting at its head, so a saturated table is covered across consecutive admissions; a pass that reaches the tail stops there (the next pass starts a fresh hand at the head), and one pass releases every seat it found so concurrent admissions do not need a second pass. Below the hard bound the pass reserves one hard-headroom seat before the walk, so a contended admission that bypasses the lock cannot take it and leave the pass rejected; at the hard bound it walks without a reservation and admits only from a reclaimed seat. Every reclaimed seat returns to the ledger. A pass that finds nothing also opens a short **Saturation Window** (50 ms) during which other new keys at the cap are rejected without another pass: a pass holds the sample lock for microseconds, so admissions that miss the lock by nanoseconds would otherwise outrun it and turn the approximate cap into a sustained bypass. The window is opened only while the ledger is still at the cap — the timer-driven **Stale Sweep** does not take the sample lock, and a pass that runs after it released seats admits instead of saturating. The window clears as soon as a pass releases a seat. The soft cap is backed by a **Hard Headroom** of `max(8, 1%)`: once the table reaches it, a new key still gets one uncontended pass and is refused only when that pass finds nothing idle, and a pass that still leaves the table at the cap re-arms the relief scan even though it reclaimed a seat. Distinct from the timer-driven **Stale Sweep**, which runs on its cadence regardless of admission pressure.
- **Saturation Window** — The 50 ms suppression that follows a completed capacity pass finding no reclaimable window (`SamplingReclaimer.tryAdmit`). The pass holds the sampler lock through its removals, so no second walk can overlap and its verdict is always the current evidence; there is no older outcome to discard. The verdict is taken against the seat ledger after the walk, so a pass over the survivors of a concurrent **Stale Sweep** admits instead of reporting a saturation that no longer holds. While it is open, a brand-new key at the tracked-key cap is rejected without another pass, except the pass's own admission, which still reserves from the Hard Headroom; the window expires on its own so a seat freed later is usable within one report interval, and a pass that reclaims a seat clears it immediately. It exists because the pass's microsecond-scale lock hold and an admission's nanosecond-scale `tryLock` failure are different orders of magnitude; without the window, every admission that lost the pass raced past the cap for as long as the pass ran.
- **Hard Headroom** — The finite bound above the tracked-key soft cap (`max(8, 1%)`), enforced by an atomic seat ledger rather than a `size()` pre-check. Every window creation reserves one seat; removal releases it under the entry monitor, and a reservation that loses a creation race is returned. Contended admissions may still fill up to the hard line, but no interleaving can exceed it. A key that already holds a HOT registry seat is exempt: its window reserves a **hot seat** above the hard line, bounded by `max-active-hot-keys`, because losing its count would make a live hot key look quiet to `COOL_FOR_LOW_QPS`. See design decisions: Worker detection.
- **Cool-down Wheel** — The Worker's schedule for due cool-down checks: a hierarchical timer wheel (1 ms base, five levels, Caffeine-shaped) whose node is the `HE` itself. A key's check is the entry's `nextCheckAt`; a deadline is placed by the XOR prefix of its time and the wheel clock, so every level holds a strictly later span than the level below and a cascade only descends. Re-arming moves the node and a cool-down unlinks it, so one entry holds exactly one check and there is no check object, queue heap, capacity cap or stale-check path. The wheels are striped by key hash, one advancing thread each (`detection.cooling.threads`); a stripe holder may take the wheel lock (stripe → wheel), while the wheel advances by appending the whole due list to the tail of the advancing thread's private batch under its lock and evaluating it lock-free after releasing it (the poll leaves each node `DETACHED` until the registry clears it under the stripe lock, and an unfinished batch stays at the head, so the next advance's entries follow it in one traversal). Each level keeps a `long` occupied-bucket word, so finding the next due bucket is a shift plus a trailing-zero count (a second count when the search wraps to the head) instead of a walk over empty sentinels; unlink clears its bit lazily on the next look. `wakeAtMs` doubles as the sleep target and the wake state (`Long.MIN_VALUE` = owner awake or signal pending), so a schedule burst collapses to one semaphore release. The wait after a batch is measured against the real monotonic clock, so the batch's evaluation time is not added to the sleep and does not hide a deadline that becomes earlier in that window. The periodic sweep only re-links entries overdue by a one-second grace; the wheel remains the only evaluator. See design decisions: worker cooling.
- **Slice Number** — The absolute index `floorDiv(monotonicMillis, sliceMs)` of a window write, stored as `KeyWindow.lastSlice`. One report batch samples the monotonic clock once and shares that instant across its keys, so the detector and the registry pay one division per batch rather than per key. The window's fast-path gate, add index, idle test and slot tags are integer arithmetic on slice numbers; the eviction retention is quantized to whole slices. `Long.MIN_VALUE` is the **Evicted Window** tombstone (the entry was removed from the map and may only be replaced). A late slot write carries its own old slice tag, so it is ignored rather than read as current traffic; a write that fell behind the whole window is dropped instead of being moved onto the newest slice.
- **Retired Entry** — A `HE` whose `belowSince` is `Long.MIN_VALUE`: it has been removed from the registry, its seat has been released, and a wheel event still holding the reference must discard it. Every removal path sets the tombstone under the key's stripe lock after the identity-matched map removal, so the un-cooled evaluation path (`fired.retired()`) needs no second `hotKeys.get`. The same field carries the LOW_QPS dwell start while the entry is live: `Long.MAX_VALUE` means "hot, not below band", and every other value is the real first below-band instant, including zero and negative monotonic coordinates.
- **TopK** — Interface for the hot key detection algorithm. Implemented by `HeavyKeeper` (Count-Min Sketch variant), the only bean of this type. Tracks the `K` most frequent keys. Queries (actuator, Micrometer, `listTopN`) inject `TopK`; writes enter through **HotKeyDetector**, which owns the lenient key contract, the tide's batch ingest and the lenient membership probe `contains(...)`, and deliberately does **not** implement the interface (two `TopK` beans decayed the same sketch twice per tick, design decisions: access counting).
- **Owned Estimate** — A sketch row contributes to a key's estimate only while the slot's fingerprint matches that key. A **collision** (a different fingerprint in the row) contributes exactly zero unless the slot changes hands — the sampled decay still applies to the occupant, but the occupant's count is never handed to the colliding key. Two paths do change hands and return the newcomer's own `delta`: the **size-aware takeover** (a strictly bigger batch, design decisions: sketch) and the **full-displacement lottery win**. Before this rule a cold key sharing a slot inherited the occupant's decayed count and could enter the TopK on someone else's traffic. See design decisions: sketch.
- **TopK Seat** — A `members` entry in the bounded TopK set. Its count is re-synchronised from the sketch's sliding window on every decay cycle, so a key whose traffic stops loses its seat once the ring rotates past its last window; halving applies only when every sketch row has been taken over. Released once the count falls below `minCount` (floor 1, so a `minCount=0` sketch still expels): below the admission threshold the key can never re-enter, so keeping its seat only starves a better candidate and depresses the O(1) fast-reject floor. Every departure — admission eviction and decay drop alike — is reported to `expelled()` with the count the key actually held. A departing node is tombstoned with the reserved negative count (`DETACHED`): a lock-free raise that resolved the node before the eviction observes the tombstone and falls through to locked re-admission instead of reporting `isHotKey = true` for an absent key. See design decisions: sketch.
- **HotKeyRule** — An operator-authored rule: match type (`EXACT` / `PREFIX` / `REGEX`), pattern, priority, `hotCount` and the flattened cool-down parameters. `coolCount > 0` selects `COOL_FOR_LOW_QPS` (`lowQpsForMs`, `checkIntervalMs`); `coolCount == 0` selects `COOL_FOR_EXPIRE` and stores its lifetime in `checkIntervalMs`. The highest-priority match governs a key; `RuleSet` is the immutable published snapshot, and its `minHotCount` is the **Promotion Floor**. `EXACT` rules are indexed by key and decide on their own threshold.
- **Lock Hierarchy** — Two locking domains in strict ordinal order: (1) HeavyKeeper sketch stripe locks (`synchronized(Object[])`), (2) HeavyKeeper admission lock (`ReentrantLock`). No code path inside a higher-order lock may acquire a lower-order lock; the cache and the window table use `ConcurrentMap.compute` and take neither.
- **SingleFlight** — Deduplication mechanism that coalesces concurrent loads for the same key into a single execution. The leader removes the flight when it settles, so a later miss re-runs the reader; it is not a completed-result cache. Prevents thundering herd. Every terminal state maps to one **LoadStatus** (`LOADED` / `SOURCE_EMPTY` / `SUPPRESSED_BREAKER` / `SUPPRESSED_TIMEOUT` / `SUPPRESSED_EXECUTOR` / `FAILED`), carried by the `LoaderOutcome` record — the reader's `null` (no data) is never conflated with suppression (protection machinery) or failure (carries the cause). Reader outcomes never throw: `HotKeyCache` alone resolves the outcome into a value or an exception, and a failed load is never a miss; the one deliberate throw is the same-thread same-key re-entry programming error described below. Each call holds one of two roles toward the flight it joined — the **Load Leader** inserted the flight and runs the reader, a **Load Follower** joined another call's flight — and only the leader commits the loaded value to L1; a follower records its own access and returns the shared value (design decisions: read path). A same-key call from inside the leader's reader is a follower whose own thread is the one running that reader; it fails fast with `IllegalStateException` instead of joining a future only it can complete. A per-key invalidation, a `clearAll`, or a scoped `clearPrefix` drops the matching flights (`invalidate` / `invalidateAll` / `invalidatePrefix`), so a read that starts after the mutation cannot join a load that began before it.
- **ElasticThreadPool** — Tomcat-style `ThreadPoolExecutor` with core→max→queue→reject ordering (vs JDK's core→queue→max→reject). Used for I/O-bound async cache operations. Backs the dedicated executor beans: `hotKeyExecutor` (bulk refresh fan-out), `interruptibleLoadExecutor` (read-miss loads and background refreshes) and `zetaSendExecutor` (broadcast sends). Its `submittedTasksCount` admission ceiling is balanced on every path that never reaches `afterExecute` — rejection (a handler throwing an `Error` included), `remove`, `purge`, `shutdownNow` — and `setMaximumPoolSize` re-derives the ceiling; the queue reads the executor's current maximum on each thread-creation decision instead of holding a snapshot. `force` and `shutdownNow` share the queue lifecycle lock, so a forced insert cannot slip past the STOP-and-drain transition.
- **PeriodicScheduler** — Exception-safe, non-overlapping periodic scheduler. `scheduleAtFixedRate` is **phase-anchored**: the cadence stays fixed to the original phase; a run that overshoots skips every missed slot and stays on the original grid (no drift, no catch-up bursts — see design decisions: scheduling). `scheduleWithFixedDelay` is completion-relative. A task exception is routed through the **ZetaExceptionHandler** chain (WARN log by default) and never kills the cadence. `remove(originalCommand)` stops a periodic chain by the original task. `shutdown()`/`shutdownNow()` terminate every chain immediately (queued next link cancelled, registry cleared, `isDone()` true at the call) instead of letting the JDK run the one-shot next link once after a full period. The chain future's `get()` waits for that terminal state; a healthy chain blocks, matching `Future` semantics.
- **ZetaExceptionHandler** — Injectable exception-handler chain (thread-local → inheritable → default → WARN-log fallback) used by all Zeta executors (`PeriodicScheduler`, `ElasticThreadPool`, `KeyDispatcher`) to report task failures without letting a task kill a worker thread. The handler receives the call-site context through a default `handleException(String, Throwable)` overload; a handler that throws is logged with the original attached as suppressed, so the failure is never masked. Inheritable values are copied at thread-creation time by the spawning thread, not registered pool-wide; `setDefaultExceptionHandler` is the process-wide path. Handlers never throw.
- **KeyDispatcher** — Per-key FIFO ordered dispatcher with **pre-granted batches**: the first task is granted at worker creation, a queued tail is folded into that first batch at the first cycle, and every later batch is drained at the end of the previous cycle. Up to `maxTasksPerCycle` same-key tasks run per underlying-executor submission, and a busy key yields afterwards so other keys progress. Queue management is a single atomic `compute` per operation (no orphan-queue race by construction); the first-cycle submission and every re-drive happen inside that `compute`, so a worker is never visible to a submitter before the executor accepted its next cycle. A full first batch waits out the remaining bounded start-jitter park (the first cycle then folds the whole burst into one grant), and `close()` cancels any remaining park. Per-key queues are bounded (`maxQueuePerKey`, excess submissions rejected); a refused first cycle publishes no worker and returns `false` to the caller (inline fallback), while a refused re-drive retires the worker and releases its queued weight. A batch's weight is settled in a `finally`, so a throwing consumer cannot leak global budget; a fatal `Error` retires the key before propagating, and an interrupt found in the cause chain is restored. The constructor rejects a non-positive per-key bound, per-cycle cap or global budget, and `submit` rejects a null key/task before admission. Both the first-merge and retire computes return the current worker unchanged when it is no longer this worker, so a successor is never deleted. The executor must not run tasks inline (no `CallerRunsPolicy` or direct executor): submission holds the key's bin lock.

## Versions

- **dataVersion** — A positive, node-local stamp allocated by the **Stamp Clock** for every data mutation and every read-path load. It is a single stamp space shared by all data paths (L1 writes, peer PUT/REFRESH/INVALIDATE, Worker HOT-create). `0` means **unknown**, not "version zero": an unknown entry makes the weakest claim and accepts any real stamp.
- **decisionVersion** — Monotonically increasing `AtomicLong` on the Worker. Orders HOT/COOL decisions. Independent of `dataVersion` and never compared with it. **Allocated at the transition, not at the send:** `HotKeyRegistry` takes it inside the per-key lock that produced the decision (the eviction COOL under its eviction lock), so version order is transition order even though the send happens later, on another thread, or behind a thousand queued keys. **Watermark semantics:** a failed send burns a version, so the sequence contains holes — it is a high-water mark of _decisions_, not a count of delivered messages. The funnel keeps the last confirmed version as its ordering watermark when a publish fails, clearing the confirmation and debounce anchor. Receivers compare with `>=` only and never assume intermediate versions exist. Delivery-side suppression is **Decision Coalescing**.
- **Stamp Clock** — `util/clock/StampClock` (production implementation `MonotonicStampClock`): the **sole** allocator of `dataVersion` on a node. `nextStamp()` returns a positive value strictly greater than every stamp returned or observed so far. `nextStamps(count)` atomically reserves a contiguous block (`[base, base+count−1]`, one CAS, bounded by the sequence window) for batched paths, so a concurrent single write orders against the whole batch at once. Load paths call it **before** reading the value: a pre-read stamp is a lower bound, so any write allocated during the load wins (design decisions: version stamps). `observe(stamp)` merges a peer stamp into the floor and reports acceptance — a stamp the forward-drift guard refuses must never be persisted as a `dataVersion`; the sync context re-stamps such a message with a fresh local stamp when the reduced per-key batch is applied, so the replacement order equals the apply order (the listener only merges accepted stamps on the consumer thread). Message trace IDs (`ReportMessage.id` and the AMQP `messageId` header on `SyncMessage`, `WorkerDecision`, `WorkerHeartbeatMessage`) are time-sortable but order nothing, so they come from the cached `TimeSource` wall clock — the stamp clock is reserved for versions.
- **Instance ID** — The per-process identifier used in per-instance queue names (`{prefix}:{instanceId}`) and in the `originInstance` header of sync messages. Resolved by `NodeIdentity`: explicit `zeta.local.instance-id`, otherwise `<server.port / SERVER_PORT / instance>-<HOSTNAME / local>-<random 8 hex>`. The random suffix is generated per resolution because neither a hostname (shared by every instance on the host) nor a process-wide UUID (shared by every context in the JVM) nor `server.port` (often only in `application.yml`, not the system properties) is unique per instance. It is the input to node-id derivation, so it must be unique per process for derived node ids to be unique.
- **JVM ID** — A random non-negative `long` minted once per JVM and exposed as `jvmId` on the actuator endpoint for process identification. It is exposure-only: no stamp or message trace ID embeds it; stamps use the **Node ID**.
- **Node ID** — The 10-bit identity (`0..1023`, 2 datacenter + 8 worker bits) in a stamp's node field. Resolved by `NodeIdentity`: explicit `zeta.local.node-id`, otherwise a stable CRC32 hash of the **Instance ID**. Distinct ids put nodes in disjoint low-bit ranges. Equal ids let two nodes mint identical stamps in the same millisecond — sequence restarts at 0 in each fresh window — and the equal-version guards then skip both directions, so the peers cannot converge. The id is logged once when first resolved; the sync listener WARNs once when a peer broadcasts under the same id (design decisions: version stamps).
- **Merge Floor** — The highest stamp this node has observed from a peer, applied through `StampClock.observe(stamp)`. Every later allocation is strictly greater than the floor, so a node whose wall clock lags cannot be permanently silenced by peers holding numerically larger stamps. Values outside `(0, Long.MAX_VALUE)` are unorderable and ignored.
- **Stamp Skew** — `StampClock.skewMillis()`: how far behind the fastest observed stamp this node is, in milliseconds. Reported as the `zeta.version.clock.skew` gauge; it bounds the convergence residual of last-writer-wins (the larger the skew, the longer conflicting peers may disagree before TTL convergence).
- **Version-Stamped Load** — Read-path invariant (design decisions: version stamps): every L1 entry created by the read path (miss load, soft-expire refresh) carries a `dataVersion` allocated **before** the value read. The resulting stamp is a lower bound on the value's age, so a concurrent write always outranks the load. A malformed (`<= 0`) incoming message is dropped rather than applied.
- **Version Guard** — `VersionGuard.shouldSkipForSync` / `shouldSkipForRefresh` compare an incoming stamp with the resident entry: a resident with `0` accepts any real stamp; an incoming `<= 0` is dropped; otherwise the strictly-newer rule applies (REFRESH additionally accepts an equal stamp, design decisions: version comparison). The decision plane uses the one `shouldSkipForWorker` guard for both HOT and COOL: a different Worker node id accepts on arrival, and an equal same-node/same-epoch decision is skipped because the lease table already stores it. The comparison is meaningful only within its own stamp space: the data-plane guards never mix in `decisionVersion`, and the decision-plane guards never mix in `dataVersion`. A missing `decisionNodeId` on either side is accepted on arrival: two anonymous decisions are not provably from the same Worker, so their epoch and version counters are not comparable.
- **Invalidation Tombstone / Clear Watermark** — `EntryLifecycle` state recording the version at which a key was invalidated and the highest table-wide `clearStamp` this node applied. `staleAgainstInvalidation(key, version)` is the one guard every L1 write path consults — peer apply, miss load, Worker preload, and the write-through apply (`putThrough` / `refresh`, the path exposed by construction because it allocates its stamp before the compute). It exists because the resident-version guard cannot judge an absent entry: a slow read that started before the invalidation would otherwise re-create the value the removal just dropped. The **writer side is the other half of the contract**: every removal records here (local `invalidate`, batch invalidate, `clearAll`, and the sync receiver's per-key/clear paths). A local-only mutation still allocates a stamp for the tombstone even though it is never broadcast — "no peer was told" says nothing about the reads already in flight on this node. A version-less (`<= 0`) write loses to any tombstone; it is outside the clear/prefix watermark order entirely, so a `clearAll` cannot refuse it and only the per-key tombstone (bounded by its own TTL) can. Scoped clears add a bounded, never-expiring second layer — an immutable `prefix → clearStamp` snapshot plus the highest live stamp — consulted between the table-wide stamp and the tombstone. The removal half is best-effort: the sweep only removes what a weakly consistent key-set iteration yields, so a fill whose guard already passed can survive the walk to its own hard TTL, the bound a peer that missed the broadcast converges under.

## Lifecycle

- **Graceful Degradation** — When the Worker cluster fails the health gate, cluster leases stop being authoritative: prewarm and cluster-scoped business actions pause, while local TopK-driven keep-warm continues because it is a per-node cost/benefit decision. No entry state changes and no TTL moves. Recovery resumes cluster actions on the next valid lease. Every degrade path is bounded and counted: the Worker's tracked-key cap rejects new keys for one eviction cycle, a saturated send executor drops INVALIDATE broadcasts while peers converge via hard TTL, and the local sketch keeps running without a reporter.
- **Renewal** — `KeepWarm`: before the resident's soft or hard deadline, load a fresh value and re-arm the resident's own declared hard/soft durations. It replaces the old value; it never extends that value's life. A failed renewal leaves every deadline untouched.
- **Decision Coalescing** — `DecisionDispatcher` keeps the newest queued decision per key. An older **HOT** with a newer decision already waiting is dropped before the queue offer (no bounded slot, no token) and counted as superseded; a HOT is dropped the same way when the registry no longer holds its promotion — the report thread can stall between the transition that allocated the version and the submission while the key cools or re-promotes, and the demotion may itself be refused, expired or failed. A queued HOT never suppresses a COOL; at submission an older COOL is always retained behind the newer decision as the fallback demotion. A COOL is elided only by the accepted version watermark or the 100 ms same-type debounce, never because the last wire state was COOL. A failed send keeps the last confirmed version and wire type but clears the confirmation and debounce anchor: a stale decision below the watermark stays suppressed, while a newer same-type decision is not debounced by a send the broker may never have received. A COOL with no accepted record is sent: the App may have promoted locally, and an earlier lifecycle's COOL may have been lost. The queue offer and the per-key record publication happen inside one `compute`, and the superseded bit decided before that offer rides the same publish, so the drain never observes a half-published item. At a token-starved head the drain applies the queue's own checks first (newer pending decision, released promotion) and then calls `WorkerBroadcaster.classify`, the same classify-plus-elide state machine the send path uses: an exact-version replay, a strictly older version and a debounced same-type decision all leave without waiting for a token and land in the same metric bucket on both paths. The record and meter are committed by `commit` only after the drain owns the item, so a shutdown withdrawal cannot be counted as accepted. `acceptedVersion` is reserved for a pre-funnel rollback (shutdown drain, unexpected round failure) that has no funnel outcome. The newest-pending map is bounded by the queues; a COOL-state accepted record is time-bounded by twice `max-decision-age-ms` while a hot record is retained until a COOL is sent, and neither is size-evicted, so every decision still allowed to travel keeps its ordering predecessor. The record is wire truth: it changes only when a HOT/COOL reaches the wire, an elision advances only its version, and a failed send keeps the last confirmed version and type while clearing the confirmation and debounce anchor because the broker may have received the message. A HOT that never reached the wire does not touch the record: it cannot have changed the cluster's state. See design decisions: decision delivery.
- **Promotion Abort** — `HotKeyRegistry.abort(key, version)` removes a HOT entry and returns its seat when the HOT decision never reached the broker: queue saturation, `max-decision-age-ms` expiry, a failed publish, or the shutdown drain. It is not a rollback of a published App decision; it means the promotion never happened. The `version` identity guard leaves a newer promotion or COOL untouched, and a HOT whose publish call failed after the broker accepted it self-corrects through the next report's newer version. Without it, `COOL_FOR_LOW_QPS` re-arms a key that stays hot and the already-hot fast path suppresses re-promotion, leaking the seat permanently. See design decisions: decision delivery.
- **Promotion Floor** — `RuleSet.minHotCount`, the lowest `hotCount` among the default and non-`EXACT` rules, derived once by `RuleSet.of` together with the precedence sort and the fingerprint. Effective `EXACT` rules are indexed by key in the published snapshot and checked before the floor; a shadowed exact rule (a higher-priority rule already matches its key) is omitted. An exact key below its own threshold is rejected before the match cache, so cold traffic for a special key cannot occupy a cache slot or advance its match counter. This keeps one special key with a low threshold from dragging every warm key into the match cache. See design decisions: Worker detection (standalone server).

- **Rule Binding** — The immutable `HotKeyRule` that judged a promotion, paired with the cumulative counters of its id. A HOT entry stores the binding for its whole life: threshold reads go through the retained rule's final fields, cooling reads the rule that promoted it, and promotion, abort and cool-out advance the captured counter handles rather than a resolver-and-metrics lookup. A publication that retains an id shares its counters with the new binding; an unchanged rule keeps its binding, while a removed id is retired and its meters are removed. See design decisions: Worker detection (standalone server).
- **Fire-and-forget** — The Worker sends each HOT/COOL decision exactly once: no periodic HOT re-broadcast, no COOL repeat, no rollback of an App's cache state when a send fails or a decision is dropped (buffer saturation, shutdown, broker outage). A decision is a statement about what was observed, not a delivery obligation; `decisionVersion` still lets receivers drop one that lost the race to the wire. The Worker's own seat is the one exception: a HOT that never reached the broker is returned via **Promotion Abort**. A lost decision converges through the coarse backstops — the App's hot hard TTL, the **Decision Validity** demotion when the Worker is gone, and the local TopK taking TTL authority — not through per-key retries. See design decisions: sync messages.
- **TTL Jitter** — Configurable one-sided random offset applied to all TTL expiry timestamps in `TtlPolicy` to prevent cache stampedes: a deadline may land up to `ratio` earlier, never later. Controlled by `zeta.local.ttl-jitter-ratio` (default 0.05); set it to `0` to disable it.
- **TTL Precedence** — A positive per-call/per-method TTL override resolves directly. A cache load, a write, a refresh and a keep-warm renewal all mint the entry's lifetime from that declaration: there is no second, heat-dependent regime. See design decisions: TTL model.
- **Packed TTL Bound** — The packed entry represents a finite duration as a unit bit plus a 31-bit magnitude, so the largest finite TTL is `2^31 - 1` seconds (about 68 years); `Long.MAX_VALUE` is the permanent sentinel. `CacheEntry.requireEncodableTtl` is the shared check used by `GetPolicy.ttlSupplier` and `EntryDraft`, so an unrepresentable value fails at the option/draft boundary instead of inside an L1 compute or a transaction's after-commit hook.

- **Expire** — Two-tier: **soft expire** (stale-while-revalidate, returns stale data + async refresh; off by default) and **hard expire** (absolute TTL, entry invalidated). Soft expire applies to every resident entry with its own soft baseline; a disabled baseline (`0`) stays disabled. The absolute deadlines are epoch-millis on the cached wall clock (`TimeSource.currentTimeMillis()`), the axis `TtlPolicy.isLogicallyExpired`/`isSoftExpired` judge. See **Strict Hard TTL** below.
- **Strict Hard TTL** — A deadline never lands later than the duration it was computed from: jitter only subtracts, a failed or empty background refresh closes the soft/retry window at the existing hard deadline instead of renewing the value, and keep-warm replaces the value under a freshly computed lifetime rather than extending the old one. Longer outage tolerance is expressed by a longer `hard-ttl-ms`, not by the framework.
- **Annotation Verbs** — `@ZetaCached` (`get`), `@ZetaPut` (`put`) and `@ZetaInvalidate` (`invalidate`): one read or write verb per method (invalidations may repeat), applied by `ZetaCacheInterceptor` through `ZetaCacheAdvisor` and auto-configured by `ZetaAnnotationAutoConfiguration` — no property and no `@EnableCaching`. A method may carry one read/write verb; a second read/write verb is a configuration error, and an invalidation cannot share the method with either. Repeated invalidations are allowed and a child declaration overrides the inherited set. `@ZetaConfig` on the bean class (or the JDK proxy's business interface), falling back to the declaring class, supplies `cache`, `hardTtl`, `softTtl`, `prewarm` and `keepWarm` defaults; attributes merge nearest-first, only an interface the method's declaring type is assignable from contributes, and two applicable sibling interfaces merge complementary attributes while a same-attribute disagreement fails startup. A composed annotation is resolved through its meta-annotation and `@AliasFor` overrides. A false `condition` bypasses a read/write or skips a removal; `eachKey` expands an array/`Iterable`; `allEntries` clears one namespace. The advisor holds only the lightweight `PlanResolver` and resolves the advice bean when the first advised bean is proxied, so the facade is not created during BeanPostProcessor registration. Every verb's plan is resolved and validated when the bean is proxied — the first pointcut question about a class scans every candidate method of the class and its interfaces, so a JDK proxy cannot defer a malformed second verb to its first call; a JDK proxy class resolves against its business interfaces, so a generic parent method shares the annotated child override's plan — so a conflicting verb, a cache name still blank after the `@ZetaConfig` fallback, a constant `condition`/`unless` that is not Boolean, a `void`/`Void` return, an unparsable key/TTL/`unless`/`condition`, an unknown or unbindable named SpEL variable (including the case where parameter names were not compiled in), a SpEL function call, an out-of-range SpEL variable (checked by walking the parsed AST, so a padded expression is still checked and a quoted literal is not a reference), a digits-only TTL literal outside `long`, a `#result` in a phase that does not bind it, a canonical positional parameter name (`pN`/`aN`) when the method compiles an expression, or a permanent synced `@ZetaPut` fails application startup rather than the first call. `cache` is the namespace, or empty to inherit the class configuration; `cache`, `hardTtl` and `softTtl` accept `${...}` placeholders resolved once at plan resolution. `key` is SpEL resolved once per call (`#p0`/`#a0`, parameter names discovered from the method that declares the verb annotation (falling back to the most-specific method and skipping compiler bridges), `#root.methodName`/`#root.method`/`#root.args`/`#root.target`/`#root.targetClass`, `@beanName`); a key that is exactly one argument reference resolves straight from the argument array, a generic `T...` tail erased to `Object[]` is copied into the implementation's component-typed array before the key is evaluated or a refresh is packed, a context-free key is folded to a constant physical key at resolution, and an empty `key` means the **Default Key**. `hardTtl`/`softTtl` are an optionally signed integer literal (surrounding whitespace stripped; `0` inherits the configured default, `-1` inherits on `hardTtl` and disables the soft window on `softTtl`, every positive value is the declared duration with `Long.MAX_VALUE` meaning never-expires, any other negative fails startup; a digits-only literal outside `long` fails startup) or a lazily evaluated SpEL expression (a context-free fold that is negative fails startup because SpEL's integer arithmetic overflows at 32 bits; a dynamic floating-point result degrades to the configured default; a huge `BigInteger`/`BigDecimal` clamps to the permanent sentinel instead of wrapping negative); `unless` vetoes the store on `@ZetaCached` and `@ZetaPut`. `#result` is bound only after the body returned: for `@ZetaCached.unless` (evaluated in `isCacheable` after the load), on a `@ZetaPut` key or TTL that reads it, and on the default after-the-body `@ZetaInvalidate` (a plain `#result.id` dereference on a null result fails; `#result?.id` yields a null key, which is a no-op removal, and an expression with its own null fallback still runs); a `@ZetaPut` key that does not read `#result` resolves before the body, its TTLs are evaluated when the write happens (a synced dynamic hard TTL is preflighted before the body), and `@ZetaCached`'s key and TTLs always resolve before the body and cannot use it. A read hands the method body to the engine as a real loader, so soft-expire (stale-while-revalidate) and SingleFlight apply; a body exception propagates unchanged and stores nothing; `null` is never stored. A public final method on a concrete class fails startup unless an interface view declares it, because a CGLIB proxy cannot override it; a `@ZetaPut` result-dependent key that resolves to null skips the write after the body (the side effect already committed).
- **Introduced Interface (Mixin)** — A view added to a proxy by `@DeclareParents` / `IntroductionAdvisor` rather than implemented by the bean. It is unrelated to a cached method's declaring type, so `PlanResolver.unwrapTarget` ignores it when deciding whether a nested proxy target still carries every method view; requiring it kept the refresh receiver on the proxy and re-entered the advice chain. An introduced interface that _extends_ the declaring type is still required, preserving the Spring Data child-interface guard. `Object` methods are never cache verbs: the interceptor skips `Object`-declared calls at invocation and the pointcut scan excludes both those and overrides of `toString`/`hashCode`/`equals`.

- **Default Key** — The canonical encoding an annotated method addresses when it declares no `key`: `[]` for no arguments, otherwise typed, self-delimiting parts (`s<len>:<text>` for a `String`, `c<len>:<text>` for a `Character`, `q<len>:<text>` for another `CharSequence`, `o<len>:<toString>` for any other object; `B:`, `S:`, `I:`, `J:`, `F:`, `D:`, `N:` (BigInteger), `E:` (BigDecimal) and `Z:` (Boolean) for the boxed scalars, without a length prefix because their text cannot contain `,` or `]`; `a<component>[...]` recursively for arrays, with primitive arrays using their JVM component letter and scalar element tags — `int[]{1}` → `aI[I:1]`, `char[]{'a'}` → `aC[c1:a]` — and `n` for a null array/collection element; `l[...]` for a `List`/other `Iterable` in iteration order, and `t[...]` for a `Set` with its encoded elements sorted so an unordered set is canonical across JVMs). Every part is self-delimiting, so argument boundaries, no arguments vs one argument, array content vs identity and `String "1"` vs `Integer 1`/`Long 1`/`BigDecimal("1")`/`'1'`/a `StringBuilder` cannot collide, and `-0.0` renders as `0.0` so numerically equal floating-point arguments address one key. A null top-level argument or a resolved null key fails the call (except an after-the-body `@ZetaPut` or `@ZetaInvalidate`, where a result-dependent null key is a no-op). A directly self-referential array or collection is rejected immediately, and an indirect cycle is rejected when a nested container repeats an ancestor on the current recursion path, or by the 32-level cap when its period exceeds that path (the same cap rejects an acyclic graph nested too deeply), so a malformed argument graph fails the call instead of overflowing the stack or expanding a branching cycle. A collection above 1024 elements is rejected instead of producing a giant key. Two limits remain: a non-array, non-collection object (a `Map` included) is rendered by `toString()`, and every reference array carries the same `aO` tag, so different component classes with coinciding element encodings (`String[]{"a"}` vs `Object[]{"a"}`) share a key — declare an explicit `key` when that matters. Implemented by `DefaultKey`.
- **Annotation Namespace** — The physical L1 key of an annotated operation: `cache + '\u0000' + key` in `TYPED` (where `key` is the explicit SpEL result or the **Default Key** encoding) or `cache + ':' + value` in `PLAIN`. The programmatic facade has no namespace, so the annotation layer encodes it; two cache names therefore never collide on the same logical key in the single L1 table, and a namespace clear is a prefix clear (`INVALIDATE_PREFIX`) rather than a table flush. `PLAIN` joins the facade's `cache:value` space; `TYPED` stays separate.
- **Read Fill** — The local L1 write performed by the load path (a miss load or a soft-expire refresh): the value is stamped by the **Stamp Clock** with the pre-read stamp and stored immediately, with no version bump of the write path, no cluster broadcast, and no transaction deferral. Distinct from **Write-Through** (`@ZetaPut` or a programmatic `put` → version bump + cluster broadcast).
- **Refresh (value-only)** — `Zeta.refresh` / `refreshAll` renew the value without changing the entry's lifecycle policy: a HOT/COOL entry keeps its state, Worker decision lease and hard deadline; a NORMAL entry keeps its stored normal hard/soft TTL baseline; only an absent or hard-expired key uses the configured defaults. A `CacheLoader` refresh uses `reload` and `isCacheable`; a TTL change is a **Write-Through** `put`, not a refresh.

- **ZetaCacheInterceptor** — The one advice behind the three annotation verbs, ordered `LOWEST_PRECEDENCE - 1` (inside method security at order 100, outside the default transaction interceptor). It resolves one **Cache Plan** per user class from the group's **most-specific method** — the source of `#root.method` and the reflective-refresh target — with SpEL parameter names coming from the annotation-declaring view (the most-specific method is the fallback), and the plan prebuilds constant TTL suppliers and the read/write/invalidation policies. The advisor's pointcut calls that resolution while Spring builds the proxy, which is the startup validation boundary; the first pointcut question about a class scans every candidate method of the class and its interfaces, folds interface-declared specifics with the same signature onto one canonical view (an interface generates no synthetic bridge, so two super-interfaces declaring the same method keep distinct `Method` objects), groups every candidate view by its bridge-resolved most-specific method, resolves each verb from the maximal annotated views (a same-verb conflict on two unrelated views is rejected), and stores the plan under every view of an annotated group, so a resolved plan then costs one map lookup on a JDK proxy too; a CGLIB proxy class shares the user class's table, and a JDK proxy class delegates to its business interfaces (a single maximal interface shares that table; several are scanned together), so the proxy's generated methods never split a generic parent method from its annotated child override. A method reported by a proxy class the user class does not implement falls back to the declaring type's table and then to a most-specific lookup. A reflective refresh selects the plan method's bridge when its declaring class generated one, otherwise it walks the declaring-type supertypes for the erased declaration on a common parent the target implements (Spring Data: `SimpleJpaRepository.findById(Object)` for `UserRepository.findById(String)`), then resolves the target's implementation of that signature. Parameter names are discovered from the method that declares the verb annotation and fall back to the most-specific method and then to remaining source views, skipping compiler bridges, so an interface declaration without metadata still binds `#name` from its implementation; when no source view carries names, a named variable fails startup instead of resolving to `null`. The interceptor resolves the key once per call (`namespace + key`), bypassing SpEL when the key is exactly one argument reference, and precomputing a no-argument default key or a context-free key at resolution; it then performs exactly one facade verb: a read passes the body as the loader to `get` and snapshots the argument array and every array reachable through its array elements before returning (a no-array hit pays no copy; each array is cloned once by identity, so a repeated array is shared and a cycle is preserved), a write resolves a result-independent key before the body, preflights a synced dynamic hard TTL before the body, then `put`s the non-null, non-vetoed result and evaluates the remaining TTLs at write time, an invalidation `invalidate`s after the body (resolving a result-independent key before the body; a `#result` key is evaluated by SpEL, a null-safe one yields a null key which is a no-op, and a fallback expression still runs; or before it, immediately, on request). The plan is keyed on the target's user class when it implements the reported method, otherwise on the most specific proxied interface that extends the declaring type (an `Advised` JDK proxy) or on the declaring type itself; the receiver is `getThis()` — already the target object, not the proxy — unwrapped once when the call scope is built and only for a nested `Advised` target. No thread-local carries policy state between layers; the one-shot refresh-bypass marker is transient and code-scoped, and the body runs on the caller thread so its transaction, security context and MDC survive. An evaluation phase builds one `ZetaEvaluationContext` from the call's immutable inputs; a write reuses its pre-body context when it has one and otherwise builds the post-body context, so `unless`, a result-dependent key and the TTLs evaluated at write time share one result-bound context, while a read's TTL supplier builds its own because the engine may evaluate it later — on a refresh thread, or inline on the caller thread — so no evaluation can observe another phase's state. A background refresh cannot resume the interceptor chain: the engine calls `CacheLoader.reload`, which the interceptor implements as a reflective invocation of the target method, normally outside transaction and method security — even when the refresh executor runs inline on the caller thread; a proxy-only fallback necessarily proceeds through the remaining advice chain with only the cache read bypassed. The read loader owns the one-shot `MethodInvocation` chain, claims it at most once, and clears it when the foreground read returns, so a refresh task that outlives the caller cannot pin the proxy, target or advice state; clearing the invocation-thread marker keeps a later inline refresh on the same thread from re-caching an evaluation context, and a refresh that must invoke the advice proxy marks that one call so the cache read is bypassed instead of serving the stale entry.

## Operations

- **L1** — Caffeine cache, App-local. The only cache tier owned by the library; every miss is a caller-supplied load (reader/loader) or, for peer-driven refreshes, the optional cluster loader.
- **Report** — Per-key frequency count sent from App to Worker via AMQP. Aggregated locally in a `WaveCounter` (hot keys aggregate writer-locally with zero contention, cold keys direct-write to the shared table; one snapshot per tide cycle) before batching; the flush cadence is the **Feed Loop**'s base interval, seeded by `zeta.local.report-interval-ms` (default 50ms).
- **Tag / TagMode** — A caller-supplied access hint that feeds the counting pipeline without a cache read. `tag(key, count, mode)` is the single-key primitive, `tagAll` the batch form; `TagMode` selects `RECORD` (shared WaveCounter), `DETECT_ONLY` (direct sketch), `REPORT_ONLY` (direct report) or `SILENT` (validated no-op).
- **Ceils (Hot Local Map)** — A writer-private open-addressing map for promoted hot keys, drained by the batch trigger or the tide. A slot holds a key, an atomic count and a tag; the tag is the publication word — a claim writes the key/count first and publishes the tag with release, a drain clears the key/bit first and publishes tag `0`, and every probe/reconcile acquires the tag. The last-key shortcut is reference equality (`key == lastKey`), so a content-equal but distinct String takes the full probe; a successful existing-slot add re-records the cache, so A-B-A traffic keeps the fast path.
- **Cold Capacity Drop** — A new cold key refused by the soft `capacity` guard; already-tracked keys keep counting. The cumulative total is `WaveCounter.coldCapacityDrops()`, separate from the reporter's dead-worker, unroutable, routing-queue and dispatcher counters; a growing value with stable traffic means the cap is undersized.
- **Report Exchange** — AMQP exchange `zeta.reportToWorker.exchange`, a **direct** exchange carrying App→Worker reports. It is separate from the **Broadcast** exchange (`zeta.send.exchange`), which carries Worker→App decisions; a report queue bound to the wrong one has consumers but no ingress.
- **Report Queue** — Per-shard durable queue `zeta.reportToWorker.<appName>.<workerNodeId>`, bound to the **Report Exchange** under routing key `reportToWorker.<appName>.<workerNodeId>`. Its consumer count is the Worker's report-consumer concurrency; queues are declared by the Worker, not the App.
- **Feed Loop** — The reporter's flush-cadence controller: it projects a smoothed arrival rate onto its current interval, scores the projection against `report-interval-target-batch`, and moves the interval by the plant's inverse (`next = last × goal / score`). `shadow` exposes the trajectory without applying it; `on` applies it and takes **Cadence Ownership**. An empty snapshot is sampled at rate zero (the window happened, nothing arrived); only delivery-censored cycles (no alive Worker) are withheld (design decisions: reporting).
- **Detector Flush Generation** — The ownership token on `AccessCounter`'s armed sketch ingest. Every arm and cancellation advances it; a scheduled task captures its generation and returns if the field has moved on. `cancel(false)` cannot stop a task that already started, so without the token an old task could clear the new task's handle and advance the detector anchor from an empty accumulator.

- **Cadence Ownership** — Which controller sets the base tide interval: the **Feed Loop** once it applies an interval, otherwise the wave pacer (whose backlog-pressure ramp is disabled for good on the first applied interval, because the loop's measured window must be the input it applied). The empty-tide ladder survives under either owner. Never shared, never returned.
- **Target Epoch** — The Worker incarnation a report was routed to, captured at routing time in `ReportMessage.targetEpoch`. The receiver drops a report whose epoch differs from its own; otherwise a durable queue or the App dispatcher could replay pre-restart windows after a restart and confirm HOT from old traffic.
- **Broadcast** — AMQP exchange `zeta.send.exchange`, a **direct** exchange carrying Worker→App HOT/COOL decisions: the Worker publishes under `send.<appName>` and every App instance queue binds under that same key, so the fan-out stays inside one tenant even on a shared broker. Cache-sync traffic (PUT / REFRESH / INVALIDATE) rides the separate fanout `zeta.sync.exchange`. Both are at-most-once; decision order is carried by the decision version, never by arrival.
- **Heartbeat** — Worker→App liveness message published to the heartbeat TopicExchange under `heartbeat.<nodeId>`, carrying the Worker's epoch, readiness and `zeta.app-name`. Every App binds `heartbeat.*`; the receiver drops a heartbeat whose app name differs from its own, so a shared broker never admits another tenant's Workers into this App's ring. A heartbeat without the app-name header is accepted for rolling-upgrade compatibility (design decisions: heartbeat and health). The worker id is read through the shared string-header reader, so a RabbitMQ `LongString` header is text rather than a body fallback; a null id is rejected at construction.
- **Dispatch Batch** — The tasks `KeyDispatcher` grants for one key in one executor cycle (at most `maxTasksPerCycle`). A batch runs on one thread, covers exactly one key (or the shared clear channel), and is **not version-ordered**: the default three AMQP consumers submit concurrently and the publisher separates channels per message type, so a batch can interleave versions from one origin or several. The consumer receives the whole list.
- **Batch Reduction** — Keeping only the highest-version message of a dispatch batch before applying anything. At an equal version the order is INVALIDATE > PUT > REFRESH, so an explicit removal wins and a value-carrying PUT is not replaced by a loader read. Every message the winner covers would be overwritten in the same call, so a covered PUT is never deserialized, a covered REFRESH never loads, and a covered INVALIDATE never takes a bin lock; every covered PUT/REFRESH/INVALIDATE still reports `onSkipped(COVERED_BY_NEWER_EVENT)` once. The winner's no-value fallback still honours an explicit INVALIDATE from the batch: it hard-removes a Worker-managed entry instead of soft-expiring it, because that removal already condemned the value. When the policy refuses or fails the winning value message before it writes, the highest covered INVALIDATE still evicts at its own version. The batch list is the only batch state — there is no per-batch context and no end-of-batch callback.
- **Invalidate Batch** — A transport frame carrying up to 1000 `[key, version]` pairs for a collection invalidation. The receiver decomposes it into per-key `INVALIDATE` tasks. It observes the frame's highest version once to merge the sender's clock upper bound, then observes each entry on its own only when the frame was refused; only an entry whose own version breaches the forward-drift bound receives a fresh local stamp, and a refused frame probe allocates none. The sender processes its own frame like a single INVALIDATE, healing a racing reload at the per-key version guard. A frame-wide replacement would raise an old accepted entry past a newer resident and evict a live value.

## Failure Behavior

- **Adaptive Heartbeat Timeout** — The per-Worker liveness window is the Jacobson/Karels estimate over heartbeat inter-arrival (`SRTT + 4×RTTVAR`, the Linux TCP RTO shape), clamped into `[adaptive-floor-ms, timeout-ms]` (design decisions: heartbeat and health). The static `timeout-ms` is the warm-up window (first 8 samples) and the ceiling, not a flat threshold; only heartbeat arrivals feed the estimator. Dead-Worker detection tightens from the static window down to a few heartbeat intervals while widening automatically under observed jitter.
- **Worker Health Gate Failed** — The cluster fails `HealthView.isClusterHealthy()`: fewer than the required threshold of observed Worker shards are alive (default threshold and its derivation: `zeta.local.heartbeat.min-alive-workers` in [CONFIG §7](docs/CONFIG.md#7-worker-listener-heartbeat-and-cluster-health); rationale: design decisions: heartbeat and health). Local TopK assumes authority: COOL entries become promotable. Worker broadcast on recovery overrides local promotions via decisionVersion.
- **Worker Partial Dead** — Some shards alive, some not. Alive shards continue normally. Dead shard's keys are routed to other shards via consistent-hashing ring reconciliation.
- **Clock Skew** — Nodes' wall clocks differ; stamps are allocated from the local clock. `StampClock.observe` raises the local floor to the fastest observed stamp, so a lagging node's later writes still win. Residual: conflicts decided while skew exists are only corrected by later writes or TTL expiry (design decisions: version stamps).
- **Stamp Regression (Rejected)** — An incoming message with `dataVersion <= 0` is malformed and is dropped; a message whose stamp is not newer than the resident entry (or not `>=` for REFRESH) is skipped. A resident entry with `0` (unknown) accepts any real stamp, restoring convergence after a restart.

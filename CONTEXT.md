# Zeta Domain Glossary

## Core Concepts

- **Hot Key** — A cache key accessed with abnormally high frequency. Ambiguous term; use **Local-Hot** (algorithm-detected) or **Worker-Hot** (`KeyState.HOT`, Worker-broadcasted) when precision matters.
- **Local-Hot** — A key whose frequency exceeds the HeavyKeeper TopK threshold on the local App instance. Triggers local L1 promotion but may differ from the cluster-wide view.
- **Worker-Hot** — A key broadcast by the Worker as HOT (`KeyState.HOT`) via AMQP. Carries a `decisionVersion` for ordering. Grants the longest L1 TTLs (1h default).
- **Worker-Cool** — A key broadcast by the Worker as COOL (`KeyState.COOL`). Signals the key is cooling down after a HOT period. Preserves original normal TTLs.
- **Detection Capability** — Recall, false-positive rate, and burst-to-promotion latency of local TopK promotion — not sketch count error. Use this term when “精确” is meant; a sketch can count accurately yet promote late.

## Cache States

- **KeyState** — Enum: `NORMAL` / `HOT` / `COOL`. HOT and COOL are set by the Worker; NORMAL is the default. Transitions: `NORMAL ↔ HOT` (via Worker broadcast or local TopK promotion), `HOT ↔ COOL` (via Worker broadcast), `HOT → NORMAL` (via Decision-Validity demotion, ADR-0035 — the issuing Worker incarnation died or restarted), `COOL → NORMAL` (via expiry + reload, or via a successful soft-expire refresh — local read activity returns the entry to the ordinary local lifecycle).
- **NORMAL** — Default state. No Worker involvement. Local TopK can freely promote to HOT.
- **HOT** — Worker-broadcasted hot decision OR local promotion result. Longest TTLs (hotHardTtl / hotSoftTtl). Never degraded or overwritten by local decisions.
- **COOL** — Worker-broadcasted cool decision. Preserved while the Worker cluster is healthy (default: at least one third of observed Workers alive, minimum 1 — see ADR-0028). Eligible for local promotion to HOT only when the health gate fails (graceful degradation mode).
- **Decision Validity** — A Worker decision stamped on an L1 entry is valid only while its issuing Worker incarnation is alive: the Worker has a health record, is alive (same freshness judgment as the ring/report path), and its current epoch equals the entry's `decisionEpoch`. On invalidity the entry is demoted in place on the next read — value preserved, normal TTLs, decision stamp cleared (ADR-0035). The Worker is the sole authority for cooling keys down; a dead or restarted Worker therefore orphans its HOT entries until the demotion returns them to the local lifecycle.

## Components

- **App** — The user's Spring Boot application that pulls `zeta` as a dependency. Runs local L1 (Caffeine), optional L2 (Redis), local TopK, and the Reporter-to-Worker AMQP link.
- **Worker** — Standalone Spring Boot application (`zeta-worker`). Consumes App reports via AMQP, runs its own TopK, emits HOT/COOL decisions back to Apps via broadcast. Published as a separate module, never deployed to Maven Central.
- **TopK** — Interface for the hot key detection algorithm. Implemented by `HeavyKeeper` (Count-Min Sketch variant). Tracks the `K` most frequent keys. The app-side facade is **HotKeyDetector** which wraps HeavyKeeper and adds a buffered `add` path for batched frequency updates.
- **Owned Estimate** — A sketch row contributes to a key's estimate only while the slot's fingerprint matches that key. A **collision** (a different fingerprint in the row) contributes exactly zero unless the slot changes hands — the sampled decay still applies to the occupant, but the occupant's count is never handed to the colliding key. Two paths do change hands and return the newcomer's own `delta`: the **size-aware takeover** (a strictly bigger batch, ADR-0092) and the **full-displacement lottery win**. Before this rule a cold key sharing a slot inherited the occupant's decayed count and could enter the TopK on someone else's traffic. See ADR-0102.
- **TopK Seat** — A `members` entry in the bounded TopK set. Released once the member's count halves below `minCount` (floor 1, so a `minCount=0` sketch still expels): below the admission threshold the key can never re-enter, so keeping its seat only starves a better candidate and depresses the O(1) fast-reject floor. Every departure — admission eviction and decay drop alike — is reported to `expelled()` with the count the key actually held.
- **FastLane** — Evaluation path that bypasses Bayesian confidence gating. Keys matching user-configured glob rules are promoted to `CONFIRMED_HOT` when the sliding-window sum reaches the rule's threshold — no confirm windows, no confidence scoring. Configured via `zeta.worker.fast-lane.*`; the path engages only when `zeta.worker.fast-lane.enabled=true` (default `false` — rules alone do not activate it). Managed at runtime by `FastLaneRuleManager`. End-to-end latency: ~60ms (P99). Rules propagate across Workers via **Fast-lane Rules Gossip** (ADR-0025).
- **Fast-lane Rules Gossip** — Worker-to-Worker propagation of the fast-lane rule set via `FastLaneRulesMessage` on the heartbeat exchange (routing key `fastlane.rules`, control-plane connection). Full-set, wall-clock-versioned, last-writer-wins with nodeId lexicographic tie-break for same-millisecond conflicts. Immediate broadcast on local mutation plus periodic broadcast every `zeta.worker.fast-lane.gossip-interval-ms` (default 60s). YAML-loaded rules start at version 0 so any gossiped set overrides them. Rule changes should be performed against a single Worker at a time. See ADR-0025.
- **ConfidenceEvaluator** — Facade over `BayesianConfidenceEstimator` that decouples the state machine from the specific estimator implementation. Injected into `ZetaBayesianSM` to gate every HOT/COOL transition.
- **BayesianConfidenceEstimator** — Normal-Normal conjugate Bayesian model for log-frequency hotness. Computes P(true frequency > threshold) as a closed-form posterior. Prior mean calibrated at ln(10). Likelihood std is dynamically adjusted via the coefficient of variation (CV) of window sums: stable traffic (CV < 0.2) tightens σ down to 0.5×, bursty traffic (CV > 0.5) loosens σ up to 3.0×.
- **ConfidenceLevel** — Three-tier classification of the Bayesian posterior probability: HIGH (≥ 0.95, broadcast immediately), MEDIUM (≥ 0.76, defer to CANDIDATE_HOT), LOW (< 0.76, suppress broadcast). Defaults defined in `ProbabilityResult` (tuning protocol in its Javadoc); overridable per-deployment via `zeta.worker.bayesian.high-confidence-threshold` / `medium-confidence-threshold`.
- **CANDIDATE_HOT** — State machine holding state for keys that crossed the hot-streak threshold but have only MEDIUM Bayesian confidence. Tracked internally, never broadcast. A single cold window drops back to COLD.
- **Lock Hierarchy** — Three locking domains in strict ordinal order: (1) state machine per-key locks (`Striped.lock`), (2) HeavyKeeper sketch stripe locks (`synchronized(Object[])`), (3) HeavyKeeper admission lock (`ReentrantLock`). The first is highest in acquisition order; the last is lowest. No code path inside a higher-order lock may acquire a lower-order lock.
- **SingleFlight** — Deduplication mechanism that coalesces concurrent loads for the same key into a single execution. Prevents thundering herd. Every terminal state maps to one **LoadStatus** (`LOADED` / `SOURCE_EMPTY` / `SUPPRESSED_BREAKER` / `SUPPRESSED_TIMEOUT` / `SUPPRESSED_EXECUTOR` / `FAILED`), carried by the `LoaderOutcome` record — the reader's `null` (no data) is never conflated with suppression (protection machinery) or failure (carries the cause). The dedup layer never throws: the caller alone applies its `failOnError` policy over the outcome.
- **SnowflakeIdGenerator** — Twitter-Snowflake style 64-bit ID generator producing time-sortable, cluster-unique IDs. Bit layout: `1s | 41ts | 2dc | 8worker | 12seq`. Uses `TimeSource` as cached clock. Worker ID derived from `InstanceIdGenerator.getNodeId()`. Attached to all message types (`ReportMessage`, `SyncMessage`, `WorkerMessage`, `WorkerHeartbeatMessage`) as trace ID via AMQP `messageId` header.
- **StandardThreadExecutor** — Tomcat-style `ThreadPoolExecutor` with core→max→queue→reject ordering (vs JDK's core→queue→max→reject). Used for I/O-bound async cache operations. Replaces `ThreadPoolTaskExecutor` in `hotKeyExecutor` bean.
- **SafeScheduledExecutorService** — Exception-safe, non-overlapping periodic scheduler. `scheduleAtFixedRate` is **phase-anchored**: the cadence stays fixed to the original phase, a run that overshoots its slot skips the missed tick and re-anchors (no drift, no catch-up bursts — see ADR-0027). `scheduleWithFixedDelay` is completion-relative. A task exception is routed through the **ZetaExceptionHandler** chain (WARN log by default) and never kills the cadence. `remove(originalCommand)` stops a periodic chain by the original task.
- **ZetaExceptionHandler** — Injectable exception-handler chain (thread-local → inheritable → default → WARN-log fallback) used by all Zeta executors (`SafeScheduledExecutorService`, `StandardThreadExecutor`, `PerKeyOrderedDispatcher`) to report task failures without letting a task kill a worker thread. Handlers never throw.
- **PerKeyOrderedDispatcher** — Per-key FIFO ordered dispatcher with **batched consumption**: up to `maxTasksPerCycle` same-key tasks run per underlying-executor submission, and a busy key yields afterwards so other keys progress. Queue management is a single atomic `compute` per operation (no orphan-queue race by construction); per-key queues are bounded (`maxQueuePerKey`, excess submissions rejected); an executor rejection is self-healed by a 200 ms re-drive retry.
- **Rule** — A cache access rule with a `pattern`, `action` (`BLOCK`/`ALLOW_NO_REPORT`/`ALLOW`), and `type` (`EXACT`/`PREFIX`/`WILDCARD`/`REGEX`). Rules are serialized to JSON for Redis persistence; **Redis is the single distribution channel** (ADR-0099): every mutation persists through the versioned Lua CAS and peers converge via a 30s daemon poll that adopts the persisted set only at or above the local version. Managed by `RuleMatcherImpl` (mutation + evaluation seams: `RuleRepository`/`RuleEvaluator`).

## Versions

- **dataVersion** — Monotonically increasing counter (Redis INCR, or degraded Snowflake fallback). Orders data mutations across instances. May be **degraded** (Snowflake-based negative space, ADR-0019) when Redis is unavailable.
- **decisionVersion** — Monotonically increasing `AtomicLong` on the Worker. Orders HOT/COOL decisions. Never degraded. Independent of dataVersion. **Watermark semantics:** allocated before each broadcast attempt, so a failed send burns a version and the sequence contains holes — it is a high-water mark of _attempts_, not a count of delivered messages. Receivers compare with `>=` only and never assume intermediate versions exist.
- **rulesVersion** — Monotonically increasing `AtomicLong` in `RuleMatcher`. Orders rule set changes across instances. Used to prevent stale rule broadcasts from overwriting newer rule sets. Independent of both dataVersion and decisionVersion.
- **Degraded Version** — A dataVersion produced when Redis is unavailable. Previously `Long.MIN_VALUE + localCounter` (per-JVM partitioned); now `Long.MIN_VALUE + SnowflakeId` (globally time-sortable, cross-instance comparable). Marked with `isVersionDegraded=true`. Always loses against a normal (Redis) version in broadcast comparisons — the `Long.MIN_VALUE` offset ensures degraded versions sort below any positive Redis INCR value.
- **Version-Stamped Load** — Read-path invariant (ADR-0033): every L1 entry created by the read path (miss load, soft-expire refresh) carries a `dataVersion` probed from Redis **after** the value read, so the stamped version is never lower than the value's true version. Probe failure withholds the stamp (fail-open) — an entry is never demoted to degraded by a failed probe. This lets the shared 4-case comparison reject late stale broadcasts, which a zero-stamped entry would admit.
- **Unstamped Claim** — The fail-open state of a **Version-Stamped Load**: the probe yielded no version, so the incoming store makes **no** version claim at all. An unstamped claim therefore never takes part in a version comparison (a resident entry cannot be "newer" than it) and never zeroes a resident's version — it preserves it. This applies identically to both L1 write paths (the load-capable store and the **Read-Miss Populate**); an unstamped claim must never be silently dropped either.
- **Batched Version Allocation** — Allocating the next `dataVersion` for a set of keys in one round trip (`VersionController.nextVersions`, pipelined per-key script executions) instead of one serial INCR per key. Used by batch invalidate so a prefix sweep costs one round trip, not N. ADR-0086's ordering is unaffected: every version is still allocated **before** any L1 drop. A batch-wide failure degrades every key to the local fallback (an invalidation is never silently dropped); a key the batch did not answer degrades alone.

## Lifecycle

- **Graceful Degradation** — When the Worker cluster fails the health gate (`HealthView.isClusterHealthy()` returns false; default: fewer than one third of observed Workers alive, minimum 1 — see ADR-0028), the App falls back to local TopK-driven TTL decisions: COOL entries become eligible for local promotion to HOT, and `isWorkerManagedEntry` checks return false. Restored automatically when a Worker heartbeat arrives.
- **Promote** — Upgrade a cache entry from NORMAL or COOL to HOT with longer TTLs. Triggered by local TopK (in `isPromotableState`) or by Worker broadcast (in `handleHot`).
- **Rebroadcast** — Periodic re-emission of a HOT decision by the Worker state machine while a key stays in `CONFIRMED_HOT`, at most once per `zeta.worker.state-machine.rebroadcast-interval-ms` (default 10s). Recovers HOT broadcasts lost in flight (fire-and-forget, ADR-0007) and caps fast-lane steady-state emission to one HOT decision per interval. The stamp (`KeyState.lastBroadcastAt`) is optimistic — set at decision time; a failed AMQP send rolls it back to 0 via `rollbackToPreviousState`, so the next evaluation retries immediately. The rollback is guarded by a per-key `mutationSeq` epoch: it applies only while no later evaluation advanced the state (a concurrent consumer's progression is never clobbered); when skipped, this periodic rebroadcast retries the failed decision instead. COOL is never rebroadcast: a lost COOL fails in the lenient direction, bounded by hard TTL and stale eviction. See ADR-0024.
- **TTL Jitter** — Configurable ±ratio random offset applied to all TTL expiry timestamps in `TtlPolicy` to prevent cache stampedes. Controlled by `zeta.local.ttl-jitter-ratio` (default 0.05 = ±5%). Always enabled.
- **TTL Precedence** — A positive per-call/per-method TTL override resolves directly for NORMAL entries. On promotion to HOT the effective hot TTL is `max(override, configured hot default)` — an override may only raise the floor, so promotion never shortens an entry's lifetime. Soft-expire (stale-while-revalidate) is governed solely by global configuration and is independent of TTL overrides; the annotation path always routes through the soft-expire entry point. (Resolved 2026-07: previously the presence of a `@CacheTtl` override silently gated soft-expire, and a small override could shorten a hot entry's TTL.)
- **Expire** — Two-tier: **soft expire** (stale-while-revalidate, returns stale data + async refresh) and **hard expire** (absolute TTL, entry invalidated). Soft expire only applies to HOT and COOL entries. See **Lease-on-Failure** below for the failure-mode amendment to the hard TTL.
- **Lease-on-Failure** — When a background soft-expire refresh fails (reader exception or timeout), the existing entry is rewritten in place with its expire timestamps extended — hard to `now + max(remaining, floor, remaining/2)` where the floor follows the entry's own scale (`min(120s, hardTtlMs)`), soft to the lease midpoint (`now + lease/2`) — value, metadata, and duration fields untouched (ADR-0036, amended by ADR-0093). A failure never shortens a healthy budget; decay toward the floor happens through wall-time passage, not halving. The lease is refused (entry left to hard-expire) for classifier-rejected failures (fatal `Error`s, plus app-supplied definitive errors), for entries older than the 30-minute staleness cap (`birthStampSec`, second precision), and when the declared hard TTL cannot fit a retry window below the refresh timeout. The stale value stays servable; the entry is soft-expired during the second half of every lease (the read-triggered retry window, so the next read re-arms the refresh). Hard TTL is therefore _not_ an absolute exit while the reader keeps failing: the trade that converts a source-outage stampede into background retry, now with a verifiable bound (lease counters + `staleDebt` view on the endpoint). Only HOT/COOL entries (the only ones with background refresh) can be leased; permanent entries are never leased; a concurrent write/broadcast/promotion that granted fresh TTLs is never shortened (identity guard on dataVersion + hardExpireAtMs); a dead Worker's orphaned HOT lease is neutralized by Decision-Validity demotion (ADR-0035) on the next read.
- **Spring Cache** — Standard `@Cacheable`/`@CachePut`/`@CacheEvict` integration via `ZetaCacheManager` (implements `CacheManager`) and `ZetaSpringCache` (implements `Cache`). Enabled via `zeta.spring-cache.enabled`. Companion annotations `@CacheTtl`, `@Intercept`, `@Fallback`, `@Preload`, `@CacheCondition`, `@Tag`, and `@SkipSync` work alongside `@Cacheable`. `null` is never cached: a `null` method result writes no entry and the next read re-invokes the method.
- **Read-Miss Populate** — The local L1 fill after a `@Cacheable(sync = false)` read miss: the business-loaded value is stamped with a read-only version probe and stored immediately, with no Redis INCR, no cluster broadcast, and no transaction deferral. Distinct from **Write-Through** (`@CachePut` → version bump + cluster broadcast).
- **ZetaCacheContext** — Thread-bound transport carrying exactly one immutable `GetOptions` (lazy TTL overrides, stale policy, reporting, failure semantics) plus a `skipSync` flag for the current cache operation. `CacheExtensionAspect` snapshots/restores it around each `@Cacheable` invocation; `ZetaSpringCache` reads the options from context. (Resolved 2026-08: replaces the former bag of per-field ThreadLocal values.)
- **CacheExtensionAspect** — Companion aspect at `@Order(HIGHEST_PRECEDENCE)` that intercepts `@Cacheable` methods, resolves SpEL key, applies `@Intercept`/`@Fallback`/`@CacheTtl` and the other companion annotations, and pushes the resolved `GetOptions` into `ZetaCacheContext` before delegating to Spring's `CacheInterceptor`. (Formerly named `HotKeyCacheExtensionAspect`.)

## Operations

- **L1** — Caffeine cache, App-local. First lookup target.
- **L2** — Optional Redis cache (or any backend via the `Supplier<T>` reader). Async fallback on L1 miss.
- **Report** — Per-key frequency count sent from App to Worker via AMQP. Aggregated locally in a `WaveCounter` (hot keys aggregate writer-locally with zero contention, cold keys direct-write to the shared table; one snapshot per 500ms delivery cycle) before batching; flush cadence `zeta.local.report-interval-ms` (default 50ms).
- **Broadcast** — AMQP exchange `zeta.send.exchange` for cross-instance sync (cache values, HOT/COOL decisions) and Worker-to-App decision delivery.
- **@Intercept** — AOP annotation for read-side interception. On interception it calls `zeta.notifyLocalDetector(key)` (local `hotKeyDetector.add()`, keeps TopK accurate and sustains local hotness so intercepted keys cannot flap) but skips the Worker report (avoids flooding Worker). Applied via `CacheExtensionAspect` on `@Cacheable` methods. (Resolved 2026-07: the local-add call was documented but missing from the aspect; restored.)
- **@Tag** — Standalone annotation (independent of `@Cacheable`) that feeds a SpEL-resolved key into the local HeavyKeeper sketch and optionally the Worker report pipeline, without a cache lookup. `skipDetection` / `skipReport` suppress each side independently. Optional `cacheName` attribute prefixes the key as `cacheName + separator + key` to align with the `@Cacheable` key namespace; empty (default) keeps the raw key namespace. Placing `@Tag` and `@Cacheable` on the same method double-counts the key (both paths feed the detector) and triggers a validator warning.
- **@CacheTtl** — Per-method TTL override annotation for read operations. Applied via `CacheExtensionAspect` on `@Cacheable` methods. (Formerly named `@HotKeyCacheTTL`.)
- **@CacheCondition** — SpEL `unless` veto with **purge semantics**: when the condition holds, the freshly computed value is not kept AND any previously cached entry for the key is actively evicted (sync respects `@SkipSync`). Unlike Spring's native `@Cacheable(unless=...)`, which only skips the new write and leaves any stale entry alive, and which is never evaluated on cache hits. `@CacheCondition` is also evaluated on hits (re-checks the cached value), enabling self-cleaning when the condition changes over time. The store-then-evict race window is bounded and accepted per ADR-0013.

## Failure Behavior

- **Worker Health Gate Failed** — The cluster fails `HealthView.isClusterHealthy()`: fewer than the required threshold of observed Worker shards are alive (default: one third, rounded up, minimum 1 — ADR-0028). Local TopK assumes authority: COOL entries become promotable, `isWorkerManagedEntry` returns false. Worker broadcast on recovery overrides local promotions via decisionVersion.
- **Worker Partial Dead** — Some shards alive, some not. Alive shards continue normally. Dead shard's keys are routed to other shards via consistent-hashing ring reconciliation.
- **Redis Degraded** — `nextVersion()` falls back to the degraded Snowflake space (`Long.MIN_VALUE | snowflakeId`, globally comparable, ADR-0019). Broadcast carries `isVersionDegraded=true`. Peers apply 4-case comparison to prevent degraded versions overwriting normal ones.

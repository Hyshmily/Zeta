# Zeta Domain Glossary

## Core Concepts

- **Hot Key** — A cache key accessed with abnormally high frequency. Ambiguous term; use **Local-Hot** (algorithm-detected) or **Worker-Hot** (`KeyState.HOT`, Worker-broadcasted) when precision matters.
- **Local-Hot** — A key whose frequency exceeds the HeavyKeeper TopK threshold on the local App instance. Triggers local L1 promotion but may differ from the cluster-wide view. Its effective state is HOT with no Worker decision (`isWorkerManaged() == false`), except during degradation, when it may retain a COOL lease as `isLocalOverrideHot()`.
- **Admission Event** — The one-time notification emitted when a key newly enters the local TopK. It feeds a bounded promoter queue and is drained off the read path. A plain read does not probe TopK membership to promote a normal NORMAL entry; the read-path exception is a NORMAL entry still carrying a COOL lease while the health gate fails. A Decision-Validity demotion re-queues a key the local TopK still contains.
- **Cacheability (loader)** — The `CacheLoader.isCacheable(value)` verdict: whether the engine may store a value it obtained on the loader's behalf (read-through load, background refresh, Worker HOT warm-up, peer REFRESH or a value-carrying peer PUT). A declined value is still served to the caller and still counts toward detection; only the L1 store is skipped. It is not a per-call bypass and not a global rule — an explicit `put` never consults it, and the key is not passed. Distinct from an **Admission Event**, which admits a key to the TopK.
- **Worker-Hot** — A key whose effective `KeyState.HOT` is owned by a live Worker HOT decision. The `DecisionStamp` carries `decisionVersion`, node ID, epoch and `DecisionKind.HOT`; `isWorkerManaged()` is true only for this state/kind pair. Grants the longest L1 TTLs (1h default).
- **Worker-Cool** — A key carrying a COOL decision lease (`DecisionKind.COOL`). Its effective state is COOL while the lease is in force; after a successful soft-expire refresh it is NORMAL while the lease remains for ordering, and a degraded local promotion may make it HOT with `isLocalOverrideHot() == true`. The lease, not the state alone, gates local promotion and health recovery.
- **Detection Capability** — Recall, false-positive rate, and burst-to-promotion latency of local TopK promotion — not sketch count error. Use this term when “精确” is meant; a sketch can count accurately yet promote late.

## Cache States

- **KeyState** — Enum: `NORMAL` / `HOT` / `COOL`, the effective TTL regime only. A Worker lease (`DecisionStamp.kind`) may outlive the state: COOL→NORMAL keeps a COOL lease, and a degraded local promotion makes a COOL-leased entry HOT with `isLocalOverrideHot()`. Transitions: `NORMAL ↔ HOT` (via Worker broadcast or local TopK promotion from an Admission Event, a load/write membership check, or a re-queued demotion), `HOT ↔ COOL` (via Worker broadcast), `HOT → NORMAL` (via Decision-Validity demotion for Worker-owned HOT, or local override cleanup), `COOL → NORMAL` (via expiry + reload, or a successful soft-expire refresh). NORMAL entries carrying a COOL lease are not promoted while the cluster is healthy.
- **NORMAL** — Default state. No Worker involvement. Local TopK promotes it to HOT when it is newly admitted, reloaded, written, or re-queued after demotion; reads do not probe membership.
- **HOT** — Worker-broadcasted hot decision OR local promotion result. Longest TTLs (hotHardTtl / hotSoftTtl). Never degraded or overwritten by local decisions.
- **COOL** — Worker-broadcasted cool decision. Preserved while the Worker cluster is healthy (see design decisions: heartbeat and health). Eligible for local promotion to HOT only when the health gate fails (graceful degradation mode, see **Promote**).
- **Decision Kind** — `DecisionKind.HOT` or `DecisionKind.COOL`, carried by a `DecisionStamp` as the lease's operation. It is separate from the effective `KeyState`: a COOL lease can sit on a NORMAL or locally overridden HOT entry. `CacheEntry.isWorkerManaged()` treats a COOL entry with a lease as Worker-owned and a HOT entry only when its lease kind is HOT.

- **WorkerDecision** — The typed App-side view of a Worker broadcast: `(id, cacheKey, WorkerType, DecisionStamp)`. `WorkerType` is `HOT` / `COOL`; the compact constructor enforces the type/stamp-kind agreement. The AMQP body and headers stay inside `WorkerDecision.from`.
- **WorkerContext** — The framework-owned guarded write path behind `WorkerPolicy`: `resolveHot` (lock-free pre-check + load/L1 fallback), `settleHot` (atomic decision/data/tombstone guard + write), `cool`, `skip`, plus the package-private `reduceCool` and `coolNow` used by the listener. A policy never implements or receives it.
- **HotAction** — `Promote(HotValue)` or `Skip(HotSkipReason)`: the outcome of `resolveHot` or of `WorkerPolicy.hot`, settled by `settleHot` so every HOT prepass receives exactly one terminal hook.
- **Batch** — A granted sync batch, sealed by shape. `Batch.Value` is a non-clear batch reduced to its effective message and carries `messages`, `winner`, the covered PUT/REFRESH messages and `coveredInvalidate`; `allowSoftExpire()` is derived from them. `Batch.Clear` keeps every table-wide and prefix clear and has no winner: the context applies them in one sweep. The policy receives it instead of re-implementing batch reduction.
- **SyncContext** — The framework-owned guarded write path for sync: `value`, `invalidate`, `clear`, `skip`.
- **Decision Validity** — A Worker decision lease stamped on an L1 entry is valid only while its issuing Worker incarnation is alive: the entry carries the Worker's ID, epoch, version and kind, and the read path resolves its `WorkerHealthRecord` in one map lookup and checks the same epoch and current liveness. A local override HOT carrying a COOL lease is not Worker-owned HOT; on recovery the read path reasserts a live COOL lease or clears a dead Worker's lease, while `isWorkerManaged()` HOT entries go through normal Decision-Validity demotion (value preserved, normal TTLs, stamp cleared). The Worker is the sole authority for cooling keys down; an entry nobody reads is bounded by the hot hard TTL.

## Components

- **App** — The user's Spring Boot application that pulls `zeta` as a dependency. Runs local L1 (Caffeine), local TopK, and the Reporter-to-Worker AMQP link. The library ships no data-access client: callers supply readers, loaders and (optionally) a cluster loader.
- **Worker** — Standalone Spring Boot application (`zeta-worker`). Consumes App reports via AMQP, runs a sliding-window detector and a rule-based promotion/cooling engine (no HeavyKeeper/TopK sketch), emits HOT/COOL decisions back to Apps via broadcast. Published as a separate module, never deployed to Maven Central.
- **Capacity Relief** — The Worker detector's behavior at the tracked-key cap (`zeta.worker.max-tracked-keys`). A new key first asks the sampler for one locked pass over 32 live windows and reclaims every one whose last write is more than a full window old — the slice-aligned boundary the read path uses, so each already sums to zero for every reader and no count is lost. A pass that finds none opens the **Saturation Window** for the arrivals behind it but still admits its own key from the **Hard Headroom**; only a full hard ledger that also finds nothing idle rejects it, and the rejection arms the next periodic scan with the window-length threshold, bounding the lockout to one scan interval. The pass walks a round-robin sweep hand over the table instead of restarting at its head, so a saturated table is covered across consecutive admissions; a pass that reaches the tail stops there (the next pass starts a fresh hand at the head), and one pass releases every seat it found so concurrent admissions do not need a second pass. Below the hard bound the pass reserves one hard-headroom seat before the walk, so a contended admission that bypasses the lock cannot take it and leave the pass rejected; at the hard bound it walks without a reservation and admits only from a reclaimed seat. Every reclaimed seat returns to the ledger. A pass that finds nothing also opens a short **Saturation Window** (50 ms) during which other new keys at the cap are rejected without another pass: a pass holds the sample lock for microseconds, so admissions that miss the lock by nanoseconds would otherwise outrun it and turn the approximate cap into a sustained bypass. The window is opened only while the ledger is still at the cap — the timer-driven **Stale Sweep** does not take the sample lock, and a pass that runs after it released seats admits instead of saturating. The window clears as soon as a pass releases a seat. The soft cap is backed by a **Hard Headroom** of `max(8, 1%)`: once the table reaches it, a new key still gets one uncontended pass and is refused only when that pass finds nothing idle, and a pass that still leaves the table at the cap re-arms the relief scan even though it reclaimed a seat. Distinct from the timer-driven **Stale Sweep**, which runs on its cadence regardless of admission pressure.
- **Saturation Window** — The 50 ms suppression that follows a completed capacity pass finding no reclaimable window (`SamplingReclaimer.tryAdmit`). The pass holds the sampler lock through its removals, so no second walk can overlap and its verdict is always the current evidence; there is no older outcome to discard. The verdict is taken against the seat ledger after the walk, so a pass over the survivors of a concurrent **Stale Sweep** admits instead of reporting a saturation that no longer holds. While it is open, a brand-new key at the tracked-key cap is rejected without another pass, except the pass's own admission, which still reserves from the Hard Headroom; the window expires on its own so a seat freed later is usable within one report interval, and a pass that reclaims a seat clears it immediately. It exists because the pass's microsecond-scale lock hold and an admission's nanosecond-scale `tryLock` failure are different orders of magnitude; without the window, every admission that lost the pass raced past the cap for as long as the pass ran.
- **Hard Headroom** — The finite bound above the tracked-key soft cap (`max(8, 1%)`), enforced by an atomic seat ledger rather than a `size()` pre-check. Every window creation reserves one seat; removal releases it under the entry monitor, and a reservation that loses a creation race is returned. Contended admissions may still fill up to the hard line, but no interleaving can exceed it. A key that already holds a HOT registry seat is exempt: its window reserves a **hot seat** above the hard line, bounded by `max-active-hot-keys`, because losing its count would make a live hot key look quiet to `COOL_FOR_LOW_QPS`. See design decisions: Worker detection.
- **Cool-down Wheel** — The Worker's schedule for due cool-down checks: a hierarchical timer wheel (1 ms base, five levels, Caffeine-shaped) whose node is the `HE` itself. A key's check is the entry's `nextCheckAt`; a deadline is placed by the XOR prefix of its time and the wheel clock, so every level holds a strictly later span than the level below and a cascade only descends. Re-arming moves the node and a cool-down unlinks it, so one entry holds exactly one check and there is no check object, queue heap, capacity cap or stale-check path. The wheels are striped by key hash, one advancing thread each (`detection.cooling.threads`); a stripe holder may take the wheel lock (stripe → wheel), while the wheel advances by appending the whole due list to the tail of the advancing thread's private batch under its lock and evaluating it lock-free after releasing it (the poll leaves each node `DETACHED` until the registry clears it under the stripe lock, and an unfinished batch stays at the head, so the next advance's entries follow it in one traversal). Each level keeps a `long` occupied-bucket word, so finding the next due bucket is a shift plus a trailing-zero count (a second count when the search wraps to the head) instead of a walk over empty sentinels; unlink clears its bit lazily on the next look. `wakeAtMs` doubles as the sleep target and the wake state (`Long.MIN_VALUE` = owner awake or signal pending), so a schedule burst collapses to one semaphore release. The wait after a batch is measured against the real monotonic clock, so the batch's evaluation time is not added to the sleep and does not hide a deadline that becomes earlier in that window. The periodic sweep only re-links entries overdue by a one-second grace; the wheel remains the only evaluator. See design decisions: worker cooling.
- **Slice Number** — The absolute index `floorDiv(monotonicMillis, sliceMs)` of a window write, stored as `KeyWindow.lastSlice`. One report batch samples the monotonic clock once and shares that instant across its keys, so the detector and the registry pay one division per batch rather than per key. The window's fast-path gate, add index, idle test and slot tags are integer arithmetic on slice numbers; the eviction retention is quantized to whole slices. `Long.MIN_VALUE` is the **Evicted Window** tombstone (the entry was removed from the map and may only be replaced). A late slot write carries its own old slice tag, so it is ignored rather than read as current traffic; a write that fell behind the whole window is dropped instead of being moved onto the newest slice.
- **Retired Entry** — A `HE` whose `belowSince` is `Long.MIN_VALUE`: it has been removed from the registry, its seat has been released, and a wheel event still holding the reference must discard it. Every removal path sets the tombstone under the key's stripe lock after the identity-matched map removal, so the un-cooled evaluation path (`fired.retired()`) needs no second `hotKeys.get`. The same field carries the LOW_QPS dwell start while the entry is live: `Long.MAX_VALUE` means "hot, not below band", and every other value is the real first below-band instant, including zero and negative monotonic coordinates.
- **TopK** — Interface for the hot key detection algorithm. Implemented by `HeavyKeeper` (Count-Min Sketch variant), the only bean of this type. Tracks the `K` most frequent keys. Queries (actuator, Micrometer, `listTopN`) inject `TopK`; writes enter through **HotKeyDetector**, which owns the lenient key contract, the tide's batch ingest and the lenient membership probe `contains(...)`, and deliberately does **not** implement the interface (two `TopK` beans decayed the same sketch twice per tick, design decisions: access counting).
- **Owned Estimate** — A sketch row contributes to a key's estimate only while the slot's fingerprint matches that key. A **collision** (a different fingerprint in the row) contributes exactly zero unless the slot changes hands — the sampled decay still applies to the occupant, but the occupant's count is never handed to the colliding key. Two paths do change hands and return the newcomer's own `delta`: the **size-aware takeover** (a strictly bigger batch, design decisions: sketch) and the **full-displacement lottery win**. Before this rule a cold key sharing a slot inherited the occupant's decayed count and could enter the TopK on someone else's traffic. See design decisions: sketch.
- **TopK Seat** — A `members` entry in the bounded TopK set. Its count is re-synchronised from the sketch's sliding window on every decay cycle, so a key whose traffic stops loses its seat once the ring rotates past its last window; halving applies only when every sketch row has been taken over. Released once the count falls below `minCount` (floor 1, so a `minCount=0` sketch still expels): below the admission threshold the key can never re-enter, so keeping its seat only starves a better candidate and depresses the O(1) fast-reject floor. Every departure — admission eviction and decay drop alike — is reported to `expelled()` with the count the key actually held.
- **HotKeyRule** — An operator-authored rule: match type (`EXACT` / `PREFIX` / `REGEX`), pattern, priority, `hotCount` and the flattened cool-down parameters. `coolCount > 0` selects `COOL_FOR_LOW_QPS` (`lowQpsForMs`, `checkIntervalMs`); `coolCount == 0` selects `COOL_FOR_EXPIRE` and stores its lifetime in `checkIntervalMs`. The highest-priority match governs a key; `RuleSet` is the immutable published snapshot, and its `minHotCount` is the **Promotion Floor**. `EXACT` rules are indexed by key and decide on their own threshold.
- **Lock Hierarchy** — Two locking domains in strict ordinal order: (1) HeavyKeeper sketch stripe locks (`synchronized(Object[])`), (2) HeavyKeeper admission lock (`ReentrantLock`). No code path inside a higher-order lock may acquire a lower-order lock; the cache and the window table use `ConcurrentMap.compute` and take neither.
- **SingleFlight** — Deduplication mechanism that coalesces concurrent loads for the same key into a single execution. The leader removes the flight when it settles, so a later miss re-runs the reader; it is not a completed-result cache. Prevents thundering herd. Every terminal state maps to one **LoadStatus** (`LOADED` / `SOURCE_EMPTY` / `SUPPRESSED_BREAKER` / `SUPPRESSED_TIMEOUT` / `SUPPRESSED_EXECUTOR` / `FAILED`), carried by the `LoaderOutcome` record — the reader's `null` (no data) is never conflated with suppression (protection machinery) or failure (carries the cause). Reader outcomes never throw: `HotKeyCache` alone resolves the outcome into a value or an exception, and a failed load is never a miss; the one deliberate throw is the same-thread same-key re-entry programming error described below. Each call holds one of two roles toward the flight it joined — the **Load Leader** inserted the flight and runs the reader, a **Load Follower** joined another call's flight — and only the leader commits the loaded value to L1; a follower records its own access and returns the shared value (design decisions: read path). A same-key call from inside the leader's reader is a follower whose own thread is the one running that reader; it fails fast with `IllegalStateException` instead of joining a future only it can complete. A per-key invalidation, a `clearAll`, or a scoped `clearPrefix` drops the matching flights (`invalidate` / `invalidateAll` / `invalidatePrefix`), so a read that starts after the mutation cannot join a load that began before it.
- **StandardThreadExecutor** — Tomcat-style `ThreadPoolExecutor` with core→max→queue→reject ordering (vs JDK's core→queue→max→reject). Used for I/O-bound async cache operations. Backs the dedicated executor beans: `hotKeyExecutor` (bulk refresh fan-out), `interruptibleLoadExecutor` (read-miss loads and background refreshes) and `zetaSendExecutor` (broadcast sends). Its `submittedTasksCount` admission ceiling is balanced on every path that never reaches `afterExecute` — rejection (a handler throwing an `Error` included), `remove`, `purge`, `shutdownNow` — and `setMaximumPoolSize` re-derives the ceiling; the queue reads the executor's current maximum on each thread-creation decision instead of holding a snapshot. `force` and `shutdownNow` share the queue lifecycle lock, so a forced insert cannot slip past the STOP-and-drain transition.
- **SafeScheduledExecutorService** — Exception-safe, non-overlapping periodic scheduler. `scheduleAtFixedRate` is **phase-anchored**: the cadence stays fixed to the original phase; a run that overshoots skips every missed slot and stays on the original grid (no drift, no catch-up bursts — see design decisions: scheduling). `scheduleWithFixedDelay` is completion-relative. A task exception is routed through the **ZetaExceptionHandler** chain (WARN log by default) and never kills the cadence. `remove(originalCommand)` stops a periodic chain by the original task. `shutdown()`/`shutdownNow()` terminate every chain immediately (queued next link cancelled, registry cleared, `isDone()` true at the call) instead of letting the JDK run the one-shot next link once after a full period.
- **ZetaExceptionHandler** — Injectable exception-handler chain (thread-local → inheritable → default → WARN-log fallback) used by all Zeta executors (`SafeScheduledExecutorService`, `StandardThreadExecutor`, `KeyDispatcher`) to report task failures without letting a task kill a worker thread. The handler receives the call-site context through a default `handleException(String, Throwable)` overload; a handler that throws is logged with the original attached as suppressed, so the failure is never masked. Inheritable values are copied at thread-creation time by the spawning thread, not registered pool-wide; `setDefaultExceptionHandler` is the process-wide path. Handlers never throw.
- **KeyDispatcher** — Per-key FIFO ordered dispatcher with **pre-granted batches**: the first task is granted at worker creation, a queued tail is folded into that first batch at the first cycle, and every later batch is drained at the end of the previous cycle. Up to `maxTasksPerCycle` same-key tasks run per underlying-executor submission, and a busy key yields afterwards so other keys progress. Queue management is a single atomic `compute` per operation (no orphan-queue race by construction); per-key queues are bounded (`maxQueuePerKey`, excess submissions rejected); an executor rejection falls back to an immediate submission, and a second rejection retires the worker and releases its queued weight. A batch's weight is settled in a `finally`, so a throwing consumer cannot leak global budget.

## Versions

- **dataVersion** — A positive, node-local stamp allocated by the **Stamp Clock** for every data mutation and every read-path load. It is a single stamp space shared by all data paths (L1 writes, peer PUT/REFRESH/INVALIDATE, Worker HOT-create). `0` means **unknown**, not "version zero": an unknown entry makes the weakest claim and accepts any real stamp.
- **decisionVersion** — Monotonically increasing `AtomicLong` on the Worker. Orders HOT/COOL decisions. Independent of `dataVersion` and never compared with it. **Allocated at the transition, not at the send:** `HotKeyRegistry` takes it inside the per-key lock that produced the decision (the eviction COOL under its eviction lock), so version order is transition order even though the send happens later, on another thread, or behind a thousand queued keys. **Watermark semantics:** a failed send burns a version, so the sequence contains holes — it is a high-water mark of _decisions_, not a count of delivered messages. Receivers compare with `>=` only and never assume intermediate versions exist. Delivery-side suppression is **Decision Coalescing**.
- **Stamp Clock** — `util/clock/StampClock` (production implementation `MonotonicStampClock`): the **sole** allocator of `dataVersion` on a node. `nextStamp()` returns a positive value strictly greater than every stamp returned or observed so far. `nextStamps(count)` atomically reserves a contiguous block (`[base, base+count−1]`, one CAS, bounded by the sequence window) for batched paths, so a concurrent single write orders against the whole batch at once. Load paths call it **before** reading the value: a pre-read stamp is a lower bound, so any write allocated during the load wins (design decisions: version stamps). `observe(stamp)` merges a peer stamp into the floor and reports acceptance — a stamp the forward-drift guard refuses must never be persisted as a `dataVersion`; the sync receiver re-stamps such a message with a fresh local stamp. Message trace IDs (`ReportMessage.id` and the AMQP `messageId` header on `SyncMessage`, `WorkerDecision`, `WorkerHeartbeatMessage`) are time-sortable but order nothing, so they come from the cached `TimeSource` wall clock — the stamp clock is reserved for versions.
- **Instance ID** — The per-process identifier used in per-instance queue names (`{prefix}:{instanceId}`) and in the `originInstance` header of sync messages. Resolved by `NodeIdentity`: explicit `zeta.local.instance-id`, otherwise `{server.port}-{HOSTNAME}` where `server.port` is read from the system property of that name (falling back to `instance`) and the host part falls back to a JVM-scoped UUID when `HOSTNAME` is absent. It is the input to node-id derivation, so it must be unique per process for derived node ids to be unique.
- **JVM ID** — A random non-negative `long` minted once per JVM and exposed as `jvmId` on the actuator endpoint for process identification. It is exposure-only: no stamp or message trace ID embeds it; stamps use the **Node ID**.
- **Node ID** — The 10-bit identity (`0..1023`, 2 datacenter + 8 worker bits) in a stamp's node field. Resolved by `NodeIdentity`: explicit `zeta.local.node-id`, otherwise a stable CRC32 hash of the **Instance ID**. Distinct ids put nodes in disjoint low-bit ranges. Equal ids let two nodes mint identical stamps in the same millisecond — sequence restarts at 0 in each fresh window — and the equal-version guards then skip both directions, so the peers cannot converge. The id is logged once when first resolved; the sync listener WARNs once when a peer broadcasts under the same id (design decisions: version stamps).
- **Merge Floor** — The highest stamp this node has observed from a peer, applied through `StampClock.observe(stamp)`. Every later allocation is strictly greater than the floor, so a node whose wall clock lags cannot be permanently silenced by peers holding numerically larger stamps. Values outside `(0, Long.MAX_VALUE)` are unorderable and ignored.
- **Stamp Skew** — `StampClock.skewMillis()`: how far behind the fastest observed stamp this node is, in milliseconds. Reported as the `zeta.version.clock.skew` gauge; it bounds the convergence residual of last-writer-wins (the larger the skew, the longer conflicting peers may disagree before TTL convergence).
- **Version-Stamped Load** — Read-path invariant (design decisions: version stamps): every L1 entry created by the read path (miss load, soft-expire refresh) carries a `dataVersion` allocated **before** the value read. The resulting stamp is a lower bound on the value's age, so a concurrent write always outranks the load. A malformed (`<= 0`) incoming message is dropped rather than applied.
- **Version Guard** — `VersionGuard.shouldSkipForSync` / `shouldSkipForRefresh` compare an incoming stamp with the resident entry: a resident with `0` accepts any real stamp; an incoming `<= 0` is dropped; otherwise the strictly-newer rule applies (REFRESH additionally accepts an equal stamp, design decisions: version comparison). The decision plane uses `shouldSkipForWorker` (COOL) and `shouldSkipForHot` (HOT): a different Worker node id accepts on arrival, and an equal same-node/same-epoch HOT decision re-applies to a `NORMAL` resident. The comparison is meaningful only within its own stamp space: the data-plane guards never mix in `decisionVersion`, and the decision-plane guards never mix in `dataVersion`.
- **Invalidation Tombstone / Clear Watermark** — `EntryLifecycle` state recording the version at which a key was invalidated and the highest table-wide `clearStamp` this node applied. `staleAgainstInvalidation(key, version)` is the one guard every L1 write path consults — peer apply, miss load, Worker preload, and the write-through apply (`putThrough` / `refresh`, the path exposed by construction because it allocates its stamp before the compute). It exists because the resident-version guard cannot judge an absent entry: a slow read that started before the invalidation would otherwise re-create the value the removal just dropped. The **writer side is the other half of the contract**: every removal records here (local `invalidate`, batch invalidate, `clearAll`, and the sync receiver's per-key/clear paths). A local-only mutation still allocates a stamp for the tombstone even though it is never broadcast — "no peer was told" says nothing about the reads already in flight on this node. A version-less (`<= 0`) write loses to any tombstone; it is outside the clear/prefix watermark order entirely, so a `clearAll` cannot refuse it and only the per-key tombstone (bounded by its own TTL) can. Scoped clears add a bounded, never-expiring second layer — an immutable `prefix → clearStamp` snapshot plus the highest stamp ever recorded — consulted between the table-wide stamp and the tombstone. The removal half is best-effort: the sweep only removes what a weakly consistent key-set iteration yields, so a fill whose guard already passed can survive the walk to its own hard TTL, the bound a peer that missed the broadcast converges under.

## Lifecycle

- **Graceful Degradation** — When the Worker cluster fails the health gate (`HealthView.isClusterHealthy()` returns false, see **Worker Health Gate Failed**), the App falls back to local TopK-driven TTL decisions: COOL entries become eligible for local promotion to HOT on the read path, NORMAL entries promote from admission/demotion events or a load/write membership check. Restored automatically when a Worker heartbeat arrives. Every degrade path is **bounded and counted, never silent death** (updated 2026-10): the Worker's tracked-key cap (design decisions: Worker detection) rejects new keys for one eviction cycle instead of OOMing the decision plane; a saturated send executor drops INVALIDATE broadcasts (counted in `BroadcastBuffer.invalidatesDropped`) while peers converge via hard TTL; the shared access counter keeps feeding the local sketch when the Worker reporter is absent (design decisions: access counting).
- **Promote** — Upgrade a cache entry from NORMAL or COOL to HOT with longer TTLs. Plain NORMAL promotion is triggered by an Admission Event drained off the read path, by a load/write membership check, or by a re-queued demotion. COOL promotion, and promotion of a NORMAL entry still carrying a COOL lease, run on the read path only while the Worker health gate fails. A Worker broadcast also promotes (through `WorkerPolicy.hot` and `settleHot`). The TTL floor a promotion applies is **TTL Precedence**; the degradation rule is design decisions: hot state.
- **Decision Coalescing** — `DecisionDispatcher` keeps the newest queued decision per key. An older **HOT** with a newer decision already waiting is dropped before the queue offer (no bounded slot, no token) and counted as superseded; a HOT is dropped the same way when the registry no longer holds its promotion — the report thread can stall between the transition that allocated the version and the submission while the key cools or re-promotes, and the demotion may itself be refused, expired or failed. A queued HOT never suppresses a COOL; a COOL is elided only when the accepted record already holds the key cold. A COOL with no accepted record is sent: the App may have promoted locally, and an earlier lifecycle's COOL may have been lost. The queue offer and the per-key record publication happen inside one `compute`, and the superseded bit decided before that offer rides the same publish, so the drain never observes a half-published item. At a token-starved head the drain applies the queue's own checks first (newer pending decision, released promotion) and then calls `WorkerBroadcaster.classify`, the same classify-plus-elide state machine the send path uses: an exact-version replay, a strictly older version, a redundant COOL and a debounced same-type decision all leave without waiting for a token and land in the same metric bucket on both paths. The record and meter are committed by `commit` only after the drain owns the item, so a shutdown withdrawal cannot be counted as accepted. `acceptedVersion` is reserved for a pre-funnel rollback (shutdown drain, unexpected round failure) that has no funnel outcome. The newest-pending map is bounded by the queues; a cold (or UNKNOWN) accepted record is time-bounded by twice `max-decision-age-ms` while a hot record is retained until a COOL is accepted, and neither is size-evicted, so every decision still allowed to travel keeps its ordering predecessor. The record keeps its version and send anchor across a failed HOT: only its cold knowledge is cleared, so older decisions stay superseded and the corrective COOL is not elided; a later superseded HOT does not re-establish cold knowledge. See design decisions: decision delivery.
- **Promotion Abort** — `HotKeyRegistry.abort(key, version)` removes a HOT entry and returns its seat when the HOT decision never reached the broker: queue saturation, `max-decision-age-ms` expiry, a failed publish, or the shutdown drain. It is not a rollback of a published App decision; it means the promotion never happened. The `version` identity guard leaves a newer promotion or COOL untouched, and a HOT whose publish call failed after the broker accepted it self-corrects through the next report's newer version. Without it, `COOL_FOR_LOW_QPS` re-arms a key that stays hot and the already-hot fast path suppresses re-promotion, leaking the seat permanently. See design decisions: decision delivery.
- **Promotion Floor** — `RuleSet.minHotCount`, the lowest `hotCount` among the default and non-`EXACT` rules, derived once by `RuleSet.of` together with the precedence sort and the fingerprint. Effective `EXACT` rules are indexed by key in the published snapshot and checked before the floor; a shadowed exact rule (a higher-priority rule already matches its key) is omitted. An exact key below its own threshold is rejected before the match cache, so cold traffic for a special key cannot occupy a cache slot or advance its match counter. This keeps one special key with a low threshold from dragging every warm key into the match cache. See design decisions: Worker detection (standalone server).

- **Rule Binding** — The immutable `HotKeyRule` that judged a promotion, paired with the cumulative counters of its id. A HOT entry stores the binding for its whole life: threshold reads go through the retained rule's final fields, cooling reads the rule that promoted it, and promotion, abort and cool-out advance the captured counter handles rather than a resolver-and-metrics lookup. A publication that retains an id shares its counters with the new binding; an unchanged rule keeps its binding, while a removed id is retired and its meters are removed. See design decisions: Worker detection (standalone server).
- **Fire-and-forget** — The Worker sends each HOT/COOL decision exactly once: no periodic HOT re-broadcast, no COOL repeat, no rollback of an App's cache state when a send fails or a decision is dropped (buffer saturation, shutdown, broker outage). A decision is a statement about what was observed, not a delivery obligation; `decisionVersion` still lets receivers drop one that lost the race to the wire. The Worker's own seat is the one exception: a HOT that never reached the broker is returned via **Promotion Abort**. A lost decision converges through the coarse backstops — the App's hot hard TTL, the **Decision Validity** demotion when the Worker is gone, and the local TopK taking TTL authority — not through per-key retries. See design decisions: sync messages.
- **TTL Jitter** — Configurable ±ratio random offset applied to all TTL expiry timestamps in `TtlPolicy` to prevent cache stampedes. Controlled by `zeta.local.ttl-jitter-ratio` (default 0.05 = ±5%); set the ratio to `0` to disable it.
- **TTL Precedence** — A positive per-call/per-method TTL override resolves directly for NORMAL entries. On promotion to HOT the effective hot TTL is `max(override, normalHardTtlMs, configured hot default)` (soft: `max(override, normalSoftTtlMs, configured hot default)`) when the promoting load/write carries an override — the resident's normal baseline and the configured hot default are floors, so promotion never shortens an entry's lifetime. Event-driven promotion has no call context, so it resolves `max(normalHardTtlMs, configured hot default)`; a later load/write with an override can only raise it. Soft-expire (stale-while-revalidate) is governed solely by global configuration and is independent of TTL overrides; annotated reads always route through the soft-expire entry point (the method body is handed to `get` as a loader). See design decisions: TTL model.
- **Expire** — Two-tier: **soft expire** (stale-while-revalidate, returns stale data + async refresh) and **hard expire** (absolute TTL, entry invalidated). Soft expire applies to NORMAL, HOT, and COOL entries (HOT/COOL use the hot soft TTL). See **Lease-on-Failure** below for the failure-mode amendment to the hard TTL.
- **Lease-on-Failure** — When a background soft-expire refresh fails (reader exception or timeout), the existing entry is rewritten in place with its expire timestamps extended — hard to `now + max(remaining, floor, remaining/2)` where the floor follows the entry's own scale (`min(120s, hardTtlMs)`), soft to the lease midpoint (`now + lease/2`) — value, metadata, and duration fields untouched (design decisions: expiry and refresh). A failure never shortens a healthy budget; decay toward the floor happens through wall-time passage, not halving. A refused lease must not leave the entry soft-expired while hard-valid: classifier-rejected failures (fatal `Error`s, plus app-supplied definitive errors) hard-expire the entry immediately, while the 30-minute staleness cap (`birthStampSec`, second precision) and a hard TTL too short for a retry window move the soft deadline up to the existing hard deadline — servable until that bound, but no read re-arms the failing refresh. A granted lease keeps the stale value servable; the entry is soft-expired during the second half of the lease (the read-triggered retry window, so the next read re-arms the refresh). Hard TTL is therefore _not_ an absolute exit while the reader keeps failing: the trade that converts a source-outage stampede into background retry, now with a verifiable bound (`refreshFailureLeased` + the `staleDebt` view on the endpoint). Only entries with a background refresh (NORMAL, HOT, or COOL) can be leased; permanent entries (`hardExpireAtMs == Long.MAX_VALUE`) are never leased; a concurrent write/broadcast/promotion that granted fresh TTLs is never shortened (identity guard on dataVersion + hardExpireAtMs); a dead Worker's orphaned HOT lease is neutralized by Decision-Validity demotion (design decisions: hot state) on the next read.
- **Annotation Verbs** — `@ZetaCached` (`get`), `@ZetaPut` (`put`) and `@ZetaInvalidate` (`invalidate`): one verb per method, applied by `ZetaCacheInterceptor` through `ZetaCacheAdvisor` and auto-configured by `ZetaAnnotationAutoConfiguration` — no property and no `@EnableCaching`. A method may carry exactly one verb; a second one is a configuration error, and two views declaring the same verb with different attributes are also rejected (a verb on the implementation method wins over the same verb on a view). Every verb's plan is resolved and validated when the bean is proxied — the first pointcut question about a class scans every candidate method of the class and its interfaces, so a JDK proxy cannot defer a malformed second verb to its first call — so a conflicting verb, a blank `cache`, a `void`/`Void` return, an unparsable key/TTL/`unless`, an unknown (when parameter names are discoverable) or out-of-range SpEL variable (checked by walking the parsed AST, so a padded expression is still checked and a quoted literal is not a reference), a digits-only TTL literal outside `long`, a pre-body `#result`, a reserved parameter name (`root`, `this`, `result`, canonical `pN`/`aN`) when the method compiles an expression, or a permanent synced `@ZetaPut` fails application startup rather than the first call. `cache` is the required namespace; `cache`, `hardTtl` and `softTtl` accept `${...}` placeholders resolved once at plan resolution. `key` is SpEL resolved once per call (`#p0`/`#a0`, parameter names discovered from the most-specific implementation method, `#root.methodName`/`#root.method`/`#root.args`/`#root.target`/`#root.targetClass`, `@beanName`); a key that is exactly one argument reference resolves straight from the argument array, and an empty `key` means the **Default Key**. `hardTtl`/`softTtl` are an optionally signed integer literal (surrounding whitespace stripped; negative clamps to 0, then folded to a constant at resolution; a digits-only literal outside `long` fails startup) or a lazily evaluated SpEL expression (a huge `BigInteger`/`BigDecimal` clamps to the permanent sentinel instead of wrapping negative); `unless` vetoes the store on `@ZetaCached` and `@ZetaPut`. `#result` is bound only after the body returned: for `@ZetaCached.unless` (evaluated in `isCacheable` after the load), on a `@ZetaPut` key or TTL that reads it, and on the default after-the-body `@ZetaInvalidate` (a plain `#result.id` dereference on a null result fails; `#result?.id` yields a null key, which is a no-op removal, and an expression with its own null fallback still runs); a `@ZetaPut` key that does not read `#result` resolves before the body, its TTLs are evaluated when the write happens (a synced dynamic hard TTL is preflighted before the body), and `@ZetaCached`'s key and TTLs always resolve before the body and cannot use it. A read hands the method body to the engine as a real loader, so soft-expire (stale-while-revalidate) and SingleFlight apply; a body exception propagates unchanged and stores nothing; `null` is never stored.
- **Default Key** — The canonical encoding an annotated method addresses when it declares no `key`: `[]` for no arguments, otherwise typed, self-delimiting parts (`s<len>:<text>` for a `String`, `c<len>:<text>` for a `Character`, `q<len>:<text>` for another `CharSequence`, `o<len>:<toString>` for any other object; `B:`, `S:`, `I:`, `J:`, `F:`, `D:`, `N:` (BigInteger), `E:` (BigDecimal) and `Z:` (Boolean) for the boxed scalars, without a length prefix because their text cannot contain `,` or `]`; `a<component>[...]` recursively for arrays, with primitive arrays using their JVM component letter and scalar element tags — `int[]{1}` → `aI[I:1]`, `char[]{'a'}` → `aC[c1:a]` — and `n` for a null array element). Every part is self-delimiting, so argument boundaries, no arguments vs one argument, array content vs identity and `String "1"` vs `Integer 1`/`Long 1`/`BigDecimal("1")`/`'1'`/a `StringBuilder` cannot collide, and `-0.0` renders as `0.0` so numerically equal floating-point arguments address one key. A null top-level argument or a resolved null key fails the call (except an after-the-body invalidation, where a result-dependent null key is a no-op removal). A directly self-referential array is rejected immediately, and an indirect cycle is rejected when a nested reference array repeats an ancestor on the current recursion path, or by the 32-level cap when its period exceeds that path (the same cap rejects an acyclic graph nested too deeply), so a malformed argument graph fails the call instead of overflowing the stack or expanding a branching cycle. Two limits remain: a non-array object is rendered by `toString()`, and every reference array carries the same `aO` tag, so different component classes with coinciding element encodings (`String[]{"a"}` vs `Object[]{"a"}`) share a key — declare an explicit `key` when that matters. Implemented by `DefaultKey`.
- **Annotation Namespace** — The physical L1 key of an annotated operation: `cache + '\u0000' + key`, where `key` is the explicit SpEL result or the **Default Key** encoding. The programmatic facade has no namespace, so the annotation layer encodes it; two cache names therefore never collide on the same logical key in the single L1 table, and a namespace clear is a prefix clear (`INVALIDATE_PREFIX`) rather than a table flush.
- **Read Fill** — The local L1 write performed by the load path (a miss load or a soft-expire refresh): the value is stamped by the **Stamp Clock** with the pre-read stamp and stored immediately, with no version bump of the write path, no cluster broadcast, and no transaction deferral. Distinct from **Write-Through** (`@ZetaPut` or a programmatic `put` → version bump + cluster broadcast).

- **ZetaCacheInterceptor** — The one advice behind the three annotation verbs, ordered `LOWEST_PRECEDENCE - 1` (inside method security at order 100, outside the default transaction interceptor). It resolves one plan per user class from the **most-specific implementation method** — the source of SpEL parameter names, `#root.method` and the reflective-refresh target — and prebuilds constant TTL suppliers and the read/write/invalidation policies there. The advisor's pointcut calls that resolution while Spring builds the proxy, which is the startup validation boundary; the first pointcut question about a class scans every candidate method of the class and its interfaces, groups every candidate view by its most-specific method, resolves each verb from the implementation method or from the group's own annotations (a same-verb conflict on two views is rejected), and stores the plan under every view of an annotated group, so a resolved plan then costs one map lookup on a JDK proxy too; a CGLIB proxy class shares the user class's table, and only a proxy-declared method the user class does not implement falls back to a most-specific lookup. Parameter names are discovered from the most-specific method and fall back to the declaring interface method, so a JDK proxy generated without `-parameters` still binds `#name`. The interceptor resolves the key once per call (`namespace + key`), bypassing SpEL when the key is exactly one argument reference, and precomputing a no-argument default key or a whole-literal key at resolution; it then performs exactly one facade verb: a read passes the body as the loader to `get`, a write resolves a result-independent key before the body, preflights a synced dynamic hard TTL before the body, then `put`s the non-null, non-vetoed result and evaluates the remaining TTLs at write time, an invalidation `invalidate`s after the body (resolving a result-independent key before the body; a `#result` key is evaluated by SpEL, a null-safe one yields a null key which is a no-op, and a fallback expression still runs; or before it, immediately, on request). The target class is `MethodInvocation.getThis().getClass()` for an ordinary target and the ultimate class only for a `TargetClassAware` nested proxy; the receiver is `getThis()` — already the target object, not the proxy — unwrapped once when the call scope is built and only for a nested `Advised` target. No thread-local carries state between layers; the body runs on the caller thread so its transaction, security context and MDC survive. An evaluation phase builds one `ZetaEvaluationContext` from the call's immutable inputs; a write shares its post-body context across `unless`, a result-dependent key and the TTLs evaluated at write time, while a read's TTL supplier builds its own because the engine may evaluate it later — on a refresh thread, or inline on the caller thread — so no evaluation can observe another phase's state. A background refresh cannot resume the interceptor chain: the engine calls `CacheLoader.reload`, which the interceptor implements as a reflective invocation of the target method outside transaction and method security — even when the refresh executor runs inline on the caller thread. The read loader owns the one-shot `MethodInvocation` chain, claims it at most once, and clears it when the foreground read returns, so a refresh task that outlives the caller cannot pin the proxy, target or advice state.

## Operations

- **L1** — Caffeine cache, App-local. The only cache tier owned by the library; every miss is a caller-supplied load (reader/loader) or, for peer-driven refreshes, the optional cluster loader.
- **Report** — Per-key frequency count sent from App to Worker via AMQP. Aggregated locally in a `WaveCounter` (hot keys aggregate writer-locally with zero contention, cold keys direct-write to the shared table; one snapshot per tide cycle) before batching; the flush cadence is the **Feed Loop**'s base interval, seeded by `zeta.local.report-interval-ms` (default 50ms).
- **Report Exchange** — AMQP exchange `zeta.reportToWorker.exchange`, a **direct** exchange carrying App→Worker reports. It is separate from the **Broadcast** exchange (`zeta.send.exchange`), which carries Worker→App decisions; a report queue bound to the wrong one has consumers but no ingress.
- **Report Queue** — Per-shard durable queue `zeta.reportToWorker.<appName>.<workerNodeId>`, bound to the **Report Exchange** under routing key `reportToWorker.<appName>.<workerNodeId>`. Its consumer count is the Worker's report-consumer concurrency; queues are declared by the Worker, not the App.
- **Feed Loop** — The reporter's flush-cadence controller: it projects a smoothed arrival rate onto its current interval, scores the projection against `report-interval-target-batch`, and moves the interval by the plant's inverse (`next = last × goal / score`). `shadow` exposes the trajectory without applying it; `on` applies it and takes **Cadence Ownership**. An empty snapshot is sampled at rate zero (the window happened, nothing arrived); only delivery-censored cycles (no alive Worker) are withheld (design decisions: reporting).
- **Cadence Ownership** — Which controller sets the base tide interval: the **Feed Loop** once it applies an interval, otherwise the wave pacer (whose backlog-pressure ramp is disabled for good on the first applied interval, because the loop's measured window must be the input it applied). The empty-tide ladder survives under either owner. Never shared, never returned.
- **Target Epoch** — The Worker incarnation a report was routed to, captured at routing time in `ReportMessage.targetEpoch`. The receiver drops a report whose epoch differs from its own; otherwise a durable queue or the App dispatcher could replay pre-restart windows after a restart and confirm HOT from old traffic.
- **Broadcast** — AMQP exchange `zeta.send.exchange`, a **direct** exchange carrying Worker→App HOT/COOL decisions: the Worker publishes under `send.<appName>` and every App instance queue binds under that same key, so the fan-out stays inside one tenant even on a shared broker. Cache-sync traffic (PUT / REFRESH / INVALIDATE) rides the separate fanout `zeta.sync.exchange`. Both are at-most-once; decision order is carried by the decision version, never by arrival.
- **Heartbeat** — Worker→App liveness message published to the heartbeat TopicExchange under `heartbeat.<nodeId>`, carrying the Worker's epoch, readiness and `zeta.app-name`. Every App binds `heartbeat.*`; the receiver drops a heartbeat whose app name differs from its own, so a shared broker never admits another tenant's Workers into this App's ring. A heartbeat without the app-name header is accepted for rolling-upgrade compatibility (design decisions: heartbeat and health).
- **Dispatch Batch** — The tasks `KeyDispatcher` grants for one key in one executor cycle (at most `maxTasksPerCycle`). A batch runs on one thread, covers exactly one key (or the shared clear channel), and is **not version-ordered**: the default three AMQP consumers submit concurrently and the publisher separates channels per message type, so a batch can interleave versions from one origin or several. The consumer receives the whole list.
- **Batch Reduction** — Keeping only the highest-version message of a dispatch batch before applying anything. Every message it covers would be overwritten by that winner in the same call, so a covered PUT is never deserialized, a covered REFRESH never loads, and a covered INVALIDATE never takes a bin lock; covered PUT/REFRESH messages still report `onRefreshSkipped` once. The winner's no-value fallback still honours an explicit INVALIDATE from the batch: it hard-removes a Worker-managed entry instead of soft-expiring it, because that removal already condemned the value. The batch list is the only batch state — there is no per-batch context and no end-of-batch callback.

## Failure Behavior

- **Adaptive Heartbeat Timeout** — The per-Worker liveness window is the Jacobson/Karels estimate over heartbeat inter-arrival (`SRTT + 4×RTTVAR`, the Linux TCP RTO shape), clamped into `[adaptive-floor-ms, timeout-ms]` (design decisions: heartbeat and health). The static `timeout-ms` is the warm-up window (first 8 samples) and the ceiling, not a flat threshold; only heartbeat arrivals feed the estimator. Dead-Worker detection tightens from the static window down to a few heartbeat intervals while widening automatically under observed jitter.
- **Worker Health Gate Failed** — The cluster fails `HealthView.isClusterHealthy()`: fewer than the required threshold of observed Worker shards are alive (default threshold and its derivation: `zeta.local.heartbeat.min-alive-workers` in [CONFIG §7](docs/CONFIG.md#7-worker-listener-heartbeat-and-cluster-health); rationale: design decisions: heartbeat and health). Local TopK assumes authority: COOL entries become promotable. Worker broadcast on recovery overrides local promotions via decisionVersion.
- **Worker Partial Dead** — Some shards alive, some not. Alive shards continue normally. Dead shard's keys are routed to other shards via consistent-hashing ring reconciliation.
- **Clock Skew** — Nodes' wall clocks differ; stamps are allocated from the local clock. `StampClock.observe` raises the local floor to the fastest observed stamp, so a lagging node's later writes still win. Residual: conflicts decided while skew exists are only corrected by later writes or TTL expiry (design decisions: version stamps).
- **Stamp Regression (Rejected)** — An incoming message with `dataVersion <= 0` is malformed and is dropped; a message whose stamp is not newer than the resident entry (or not `>=` for REFRESH) is skipped. A resident entry with `0` (unknown) accepts any real stamp, restoring convergence after a restart.
